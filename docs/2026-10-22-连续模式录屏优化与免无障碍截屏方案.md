# 连续模式录屏优化与免无障碍截屏方案（2026-10-22）

> 目标：
> ① 连续参谋模式下，a11y 开启时录屏授权弹窗**自动确认**（零点击全自动录屏）；
> ② 封装**不依赖无障碍**的录屏截图函数（防黑白屏、帧清晰、毫秒级），
>    使「Shizuku + 录屏 + OCR + 以图找图」模式具备**反侦察**感知能力
>    （无 a11y 痕迹，规避 IM/银行类 App 的无障碍风控检测）。

## 1. 用户观察评估（结论：两点均成立）

### 观察 1：assists「请求屏幕录制权限（自动允许）」→ a11y 开时零点击录屏 ✅

vendor 源码实证（[MPManager.kt:237-281](file:///e:/_android_work/NovaBAIC/vendor/assists/assists-mp/src/main/java/com/ven/assists/mp/MPManager.kt#L237)）：`request(autoAllow=true)` 内 250ms 轮询（5s 超时）：
- 点系统弹窗「立即开始」按钮（HyperOS/MIUI）
- 处理 MIUI 屏幕共享模式下拉（spinner）选「整个屏幕」
- 点「开始」按钮（原生 Android）

我们已在用 MPManager（ImChatNavigator/FrameSource/ReadinessGate），但所有调用处都传
`autoAllow=false`——**能力已在库里，只是没开**。a11y 开启时 AssistsCore.findByTags 能找到
弹窗节点并点击 → 自动确认成立。a11y 关闭时该机制不可用（无节点树），
但 Shizuku appops 静默投影（docs/2026-10-21 方案，已落地）覆盖了这条路径。

### 观察 2：「截取当前屏幕（使用屏幕录制权限）」→ 免 a11y 截屏可封装 ✅

vendor 实现（[MPManager.kt:287-299](file:///e:/_android_work/NovaBAIC/vendor/assists/assists-mp/src/main/java/com/ven/assists/mp/MPManager.kt#L287)）：
`takeScreenshot2Bitmap()` = 常驻投影 ImageReader.`acquireLatestImage()` → Bitmap，毫秒级、零弹窗、零 a11y。

**重要归因修正**：此前「HyperOS 投影帧 ~2× 下采样模糊」的结论存疑——
vendor MPManager（L177-180）与上游 MediaProjectionService（L160-185）的
ImageReader/VirtualDisplay **均为原生全尺寸**，参数无差异；且用户实测 assists
示例（同一真机同一 HyperOS）帧清晰流畅。旧测量（方差 225 vs 714）可能来自
当时测量环节偏差或旧帧。**方案第一步安排三通道同屏复测归因**。

## 2. 现状通道矩阵

| 通道 | 依赖 | 速度 | 清晰度 | 现状 |
|---|---|---|---|---|
| a11y captureScreen | a11y 开 | 快 | 原生 | ScreenPerceiver/FrameSource 第一档 |
| Shizuku screencap | Shizuku | 慢（~1-2s shell+文件 IO） | 原生（方差 714） | FrameSource 第二档、RPA 主源 |
| 上游投影（screenshotProvider） | 投影授权（FloatCaptureActivity，拍完即关） | 快 | 存疑（旧测模糊） | ScreenPerceiver 投影档 |
| vendor MPManager 投影 | 投影授权（MPService 常驻） | 快（acquire 毫秒级） | 原生（assists 示例实测 OK） | FrameSource 兜底、RPA ensureProjection |

授权面：上游通道每次重授权（手动点弹窗）；MPManager 常驻一次授权；
appops 静默（Shizuku）免弹窗。三者的组合没有被统一编排——本方案补齐。

## 3. 方案设计

### 模块 A：连续模式录屏授权自动化（autoAllow 编排）

授权入口统一为一个策略函数（建议放 floatball/auto/ 新门面）：

```
授权策略 = a11y 开            → MPManager.request(autoAllow = true)   // 弹窗自动点
         | Shizuku Ready      → 先确保 appops PROJECT_MEDIA allow（ShizukuGrant 一条龙）
         |                      再 MPManager.request(autoAllow = false) // 静默直过
         | 其余（a11y 关且无 Shizuku）→ 手动点弹窗（现状）+ UI 明示缺项
```

改动点：ImChatNavigator.ensureProjection、FloatSettingsActivity L972、
连续模式（ScreenPerceiver/FloatBallService）发起投影处，autoAllow 按
`AssistsService.getOrNull() != null` 动态传。**不改 vendor 库**（能力已有）。

### 模块 B：封装免 a11y 截屏函数（核心新代码）

新增 `floatball/auto/ScreenCapture.kt`（薄门面，注入 ShizukuInjector）：

```kotlin
suspend fun captureNow(
    maxWaitMs: Long = 1_500,     // 首帧等待（投影刚建立时 Reader 可能空）
    qualityCheck: Boolean = true,
): Result<Bitmap>
```

内部逻辑（三层保障，防黑白屏）：
1. **主源**：`MPManager.takeScreenshot2Bitmap()`（需 `isEnable`，毫秒级）；
   Reader 空返回时短轮询等待首帧（≤maxWaitMs）。
2. **质检**：复用 FrameQuality——黑帧/白帧/空白帧检测（灰度签名 + 方差）；
   FLAG_SECURE 页面投影输出全黑帧 → 质检判死 → 走 3。
3. **兜底**：Shizuku `screencap()`（原生清晰，秒级）；
   仍失败 → `Result.failure(REASON_CAPTURE_*)` 报因（禁静默空转，§4.5.2）。

静态画面旧帧说明：acquireLatestImage 在内容无变化时可能返回旧帧——
连续参谋模式由 FrameDiffEngine 差分自然消化（旧帧不产生新事件）；
单次问答/RPA 场景靠质检 + screencap 兜底保证「当前帧」。

### 模块 C：连续模式感知面切换（ScreenPerceiver 投影档换轨）

- ScreenPerceiver 阶梯④现走上游 screenshotProvider；改为 MPManager 通道
  （常驻投影 + 模块 A 授权编排 + 模块 B 质检），连续模式与 RPA 共用一套投影基础设施。
- a11y 关 + Shizuku 时连续抽帧（0.5-2s 节奏）由投影 acquire 承担
  （毫秒级、无 shell 开销），screencap 只做质检兜底——**连续模式的反侦察感知全链无 a11y**。
- 上游 screenshotProvider 保留给主框架原有功能（聊天内截图），零改动。

### 反侦察价值（模式 2 RPA 完整闭环）

微信/银行等 App 风控常查 `enabled_accessibility_services`；本方案后：
感知（录屏抽帧 + OCR + 找图）与执行（Shizuku input/paste）全程无 a11y
痕迹，a11y 服务可保持关闭——「无障碍关闭是完整第二执行面」（AGENTS §4.5）
从执行面扩展到**连续感知面**。

## 6. 风险与边界

1. **Android 14+ 一授权一投影**：MPManager 常驻投影与上游「拍完即关」通道
   各持各的授权，互不冲突；但同一 MPManager 重复 request 需先停旧实例（vendor 已处理）。
2. **HyperOS 弹窗 UI 变更**：autoAllow 依赖节点 tags（立即开始/开始/spinner），
   ROM 大版本更新可能失效 → 失败超时后回落手动路径（不静默）。
3. **FLAG_SECURE**：系统级黑帧，无解，质检 + 报因兜底。
4. **帧内存**：全尺寸帧 ~10MB/帧，acquire 后及时 close（vendor takeScreenshot2Bitmap 已 close image）；连续模式现有 Bitmap 管理复用。
