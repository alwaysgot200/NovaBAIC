## 0. 结论先行

1. **「子菜单选了自动没反应」不是没有启动代码。** 三个入口最终都汇入 `FloatBallService.applyAutoTargets`，但启动过程存在四类可见性缺口：
   - 导航阶段（可能十几秒）球仍是蓝球，只有主页状态签在后台变化，用户看不到；
   - 主动首轮固定等 `KICKOFF_DELAY_MS = 12s`，且静默时段/已有回合时直接跳过，只写日志；
   - 成稿后默认「拟人」节奏再随机等 `8~90s`，首条消息可能 1~2 分钟才出现；
   - 若干失败分支只弹 Toast，甚至 `beginCompanion` 早退时不复位 `autoRun`，表现为「球没红、也没消息」。
2. **慢的主因可排序**：默认拟人节奏（8~90s，最大且可调）→ 发送内层固定等待（`proof` 约 2.9s、`send_shizuku` 最坏 7.1s）→ 回合准备/治理（prep 约 2.25s、gov 约 0.7~1.9s）→ LLM 首字（0.3~3.2s）→ 感知轮询（800ms×2 拍，OCR 时长已有分段账）。**不是单一环节坏了，而是多个固定等待叠加。**
3. **回复「傻」的主因正是用户判断的「未区分我/对方」**。当前 `FrameDiffEngine` 已用 `OwnBubbleLocator` 剔除我方绿气泡，只把剩余文字扁平喂给 LLM；LLM 看不到对话结构，只能对「最后一坨字」作答。本期只做防回声/防重复等稳定性加固，**完整对话结构另立项 R1**。
4. **参数已经可调**：工作/停歇默认改为 **1 分钟 / 1 分钟**，设置页可选 1/5/10/15 分钟工作、关闭/1/5/10/20 分钟停歇；回复节奏四档（快速 1~3s、标准 3~10s、拟人 8~90s、从容 30~180s），默认拟人。调试广播可一次注入。
5. **本期必须闭环的是「启动可见、失败有因、状态可复位、发送不重复」**；「对话内容正确识别」不在本期，避免再次把范围滚大。

## 2. 代码现状基线（按链路）

### 2.1 三入口与统一启动口

| 入口 | 代码入口 | 目标来源 | 是否导航 | 启动形态 |
| --- | --- | --- | --- | --- |
| 悬浮球子菜单 | `openAutoScopePicker` → `startAutoForContact` / `startAutoForAll` | 联系人 × APP 会话（`autoScopeEntries`） | 具体 APP 时 `navigate=true` | 单会话走陪伴窗口；联系人级/多会话走调度器 |
| 分屏「自动」键 | `startCompanionWindow` | 当前屏 `screenAdvisor.activeContact` + `lastChatCandidate` | `navigate=false` | 单会话陪伴窗口 |
| 主页「自动」键 | `startAutoFromMain` → `applyAutoTargets` | `AutoSelectionStore` 持久化选择集 | `navigate=true` | 单/多同左 |

三条路径最终都调用 `FloatBallService.applyAutoTargets(targets, navigate, source, announce)`。这是 2026-10-25 方案要求的「唯一启动口」，方向正确。

### 2.2 单会话与多会话

- **单会话（`targets.size == 1 && imPackage != null`）**
  1. `autoRun=true`、写 `AdvisorRunState.setAuto`；
  2. 可选 `ImChatNavigator.openChat`；
  3. `CompanionWindowController.start` 开陪伴窗口；
  4. `handleCompanionStart` 置 `mode=AUTO`、红球 + 脉冲红点、`kickoffAuto(contact)`；
  5. 陪伴窗口内：`startRecording(forCompanion=true)` 启动差分循环 → 成稿 → `Gatekeeper` → 拟人节奏 → `ActionDispatcher.dispatch`。
- **多会话 / 联系人级（`imPackage == null` 或 targets > 1）**
  1. `AutoSessionScheduler.start(targets)`；
  2. `AdvisorNotificationListener` 收到通知 → `enqueue`（3s 去抖、队列 20）；
  3. worker 串行处理：`submitNotificationTurn` → 抽取 → 硬审 → `openChat` 导航 → `dispatch`；
  4. 处理后 `COOLDOWN_MS = 4s` 再取下一条；
  5. **没有主动首轮 kickoff**，完全等通知。
- **「全部联系人」**
  - 只开启通知拟稿（`draftEnabled=true`），**不自动发送**，是安全边界，不是自动聊天。

## 3. 「选了自动没反应」根因分析

### 3.1 启动调用链

```
子菜单/分屏/主页
  └─ applyAutoTargets
       ├─ 检查 mode（仅 IDLE/RECORDING 可进）
       ├─ 自动开总闸 + 加白名单 + 持久化选择集
       ├─ 单会话（navigate=true，2026-10-27 下午起为两段式）：
       │    ① 通知 contentIntent 直达（ImNavigator，预算 3s）  ← 命中 <1s
       │       ↳ 失败（无缓存键/失效/超时）才走 ②
       │    ② openChat 视觉·搜索链（5~30s，a11y 黑洞 IM 上可能必败）
       │    → CompanionWindowController.start
       │    → mode=AUTO、红球+红点
       │    → kickoffAuto（等 12s）
       │    → 成稿 → 治理 → pace → dispatch
       └─ 多会话/联系人级：
            AutoSessionScheduler.start
            → 等通知入队（无通知则永远不动）
```

### 3.2 代码可验证的七类缺口

| # | 现象（用户视角） | 代码事实 | 后果 | 优先级 |
| --- | --- | --- | --- | --- |
| G1 | 选了之后球还是蓝的，十几秒没动静 | 单会话在 `openChat` 导航阶段只写 `AdvisorRunState`，`mode` 仍是 IDLE，球未切红 | 导航慢时完全像「没反应」 | P0 |
| G2 | 进了聊天页，但一分钟没消息 | `kickoffAuto` 固定 `delay(12_000)`；且 `tally.drafts>0` 或 `status==Thinking` 时直接跳过，只写日志 | 首条消息被推迟或永久跳过 | P0 |
| G3 | 成稿了却迟迟不发 | 默认拟人节奏 `8~90s` 随机等待；设置页默认就是拟人档 | 首条消息 1~2 分钟才出现 | P0（参数可调，已具备） |
| G4 | `beginCompanion` 早退后状态卡住 | `contactRefFor` 返回 null 或已有陪伴窗口时，只 toast 并 `return`，**不调用 `finishAutoRun`**；此时 `autoRun=true`、`AdvisorRunState` 已是 AUTO、`mode` 仍 IDLE | 球不红、无窗口、主页状态签却显示自动中 | P0 |
| G5 | 多会话选了却永远不回复 | 多会话路径只校验 `targets`，**不校验通知使用权**；调度器启动后只等 `AdvisorNotificationListener` 入队 | 没通知权限/通知被系统抑制 → 永远不动 | P0 |
| G6 | 从分屏/对话页点自动，目标不对或直接进调度器 | `resolveCurrentAutoTarget` 优先用 `lastChatCandidate`，否则用 `profile.imPackage`；若 profile 无包名但存在 `chat_channels`，**不会回退取 channel 的包名**，最终 `imPackage=null` → 走多会话调度器 | 从聊天页点自动却不开陪伴窗口，只等通知 | P0/P1 |
| G7 | 启动失败只闪一下 Toast | 导航失败、白名单满、无联系人等均只 toast；Toast 可能被 IM 前景/系统限制吞掉 | 用户无法区分「没启动」与「启动了但没消息」 | P0 |

补充事实：

- `startAutoForAll` 只打开通知拟稿并 toast，不会进入 `Mode.AUTO`；如果用户误把它当「自动聊天」，会以为没反应。这是既有的安全设计，但需要在 UI 文案和本文中写清楚。
- 多会话没有主动首轮；已有未读消息在启动前已经通知过，不会再触发 `enqueue`，所以「刚点开始，聊天里已经有对方消息」时也不会立即回复。这是 G5 之外的另一条静默路径。
- 分屏入口 `navigate=false`，默认信任当前屏幕；如果当前不是目标聊天页，会录到错误画面。需要在启动时校验前台/会话页，或在必要时导航。

### 3.3 结论

「没反应」应拆成三件事分别修：

1. **可见性**：启动即给红球+脉冲红点，状态签显示「启动中/导航中/已托管/失败原因」。
2. **状态一致性**：启动链用 `try/finally` 收口，任何失败都 `finishAutoRun`；`beginCompanion` 改为返回结果，不再早退漏复位。
3. **前置条件**：多会话启动前校验通知使用权；分屏入口校验当前会话页或回退到 channel 包名；kickoff 的 12s 缩短并显式记录跳过原因。

| 节点树 | `adb shell uiautomator dump`（微信会话页）只有 **1 个空节点**，381 字节，`bounds=[0,0][0,0] package=com.tencent.mm` | 微信 8.0.79 对第三方无障碍客户端**零暴露**节点树（连 uiautomator 都读不到） |
| 注入实现 | `AssistsA11yBridge.typeText` 依赖可编辑节点 / `ACTION_PASTE` 也依赖节点 | 模式 A（`A11yInjector`）在微信上**必然** `no_focused_input` |
| Shizuku | `pm list packages` 无 Shizuku（只有 baic2 / sogou / miui inputmethod） | 模式 B 不可用；当时 `plan` 的 auto 档只有 `[A11y]` 一条 → 整轮只剩 C 起草档 |

**结论**：这不是「证据判错」也不是「节奏太慢」，而是**执行面在本机没有可用通道**——
A 要节点树、B 要 Shizuku，两个前提在这台机器 + 微信的组合下**都不成立**。

#### 3.5.1 免 Shizuku 注入链的可复现性验证（adb 手工四步，全部成功）

| 步骤 | 手工命令（1080×2460） | 观测 |
| --- | --- | --- |
| ① 聚焦 | `input tap 540 2304`（键盘收起态输入栏，y≈0.936H） | 键盘弹起，输入行上移到 **y≈1382（0.562H）** |
| ② 长按输入行 | `input swipe 486 1382 486 1382 700` | Sogou 工具条弹出「粘贴 / 语音输入 / # / 全屏输入 / 搜一搜 / 边写边译」，「**粘贴**」中心 **(112,1274)** |
| ③ 点「粘贴」 | `input tap 112 1274` | 文本落进输入框（测试串 `TESTABC` 回到 (254,1382)），**绿键出现**，中心 (984,1381) |
| ④ 点绿键 | `input tap 984 1381` | 消息气泡上屏（右侧绿泡，y=1220）；输入框清空、绿键消失 |

追加事实（影响锚点设计）：

- **0.562H 才是本机 QWERTY 展开态的输入行中线**；旧常量 `KEYBOARD_OPEN_INPUT_Y_RATIO=0.438f`
  在本机对应的是「手写/随写」高面板态，**长按 0.438H 会落在聊天正文上**（并让微信收起键盘），

  ML Kit 识别；`tests/tools/ocr.py` 离线复核一致）。

→ 据此新增**第三种执行通道 G（手势粘贴）**，落码见 §5.4（S11）。

## 4. 「回复慢」分段归因

### 4.1 端到端公式

```
T_total ≈ T_sense + T_prep + T_llm + T_gov + T_pace + T_send
```

- `T_sense`：`pollInterval` 800ms × 稳定 2 拍 + 差分 + OCR。内容不变时不会 OCR；变化后约 2 拍才触发。
- `T_prep`：`ScreenAdvisor.executePrepared` 进入 LLM 前的准备（上下文、记忆、提示词组装）。
- `T_llm`：首字 `llm_first` + 收口 `llm_lean`。
- `T_gov`：`read/extract/gate/rewrite/regate`。
- `T_pace`：`HumanPace.randomDelayMs(min,max)` 的实际等待。
- `T_send`：`focus/inject/locate/tap/proof/send_*`。

### 4.2 真机样本（2026-10-27 12:26 前后，抽样）

| 段 | 观测值 | 说明 |
| --- | --- | --- |
| `turn` | 约 3.5s | `prep≈2.25s`，`llm_first≈0.3~3.2s` |
| `gov` | 约 0.7~1.9s | 含 read/extract/gate |
| `exec send` | `conv=17 5378ms`、`conv=27 3333ms` | 执行段总耗时 |
| `send_shizuku` | 最坏 7116ms | Shizuku 截图/确认链路 |
| 发送内层 | `focus=2309, inject=364, locate=627, tap=513, proof=2949` | `proof` 是最贵的固定等待 |
| `mode2/total` | `4424/4428ms` | 通道切换/总账样本 |
| `pace` | 默认 `8000~90000ms` | **最大的可控等待** |

> 说明：以上是单次/少量样本，不是统计均值；用于排序瓶颈，不作为 SLA。感知段已有 `wait/frame/ocr` 日志，尚未汇总成均值，复测时补采。

### 4.3 逐段判断

| 环节 | 是否主因 | 判断与对策 |
| --- | --- | --- |
| 采集屏幕 | 否（但会放大首响） | 800ms 轮询 + 2 拍稳定是设计值；投影 `fresh=false` 会复用最新帧。首响可接受，但导航/首帧期间用户感知为「没反应」。 |
| OCR | **未证明是主因** | OCR 只在差分触发时跑，已有 `ocr` 分段；当前没有证据表明单次 OCR 占用数秒。复测需采集 `ocr` 均值；若 >1.5s，再考虑降分辨率/区域裁剪。 |
| prompt 组装 | 次要 | `prep≈2.25s`，可通过精简记忆/并发取数优化，但收益小于 pace。 |
| LLM 回复 | 次要 | `llm_first 0.3~3.2s`；模型/网络决定，非本地代码可完全消除。 |
| 提取 LLM 回复 | 次要 | 含在 `gov/extract` 的 0.7~1.9s 内。 |
| RPA 动作 | **第二主因** | `send` 3.3~7.1s；`proof≈2.9s`、`send_shizuku≈7.1s` 是固定等待/截图确认。可优化但必须保留防错。 |
| 拟人节奏 | **第一主因** | 默认 8~90s 随机；用户感知最强烈，且已有四档可调。 |

### 4.4 慢的两种口径

- **「首条消息」慢**：12s kickoff + prep/LLM/gov（约 3~7s）+ pace（8~90s）+ send（3~7s），最坏可到 1~2 分钟。
- **「后续回复」慢**：对方来信后，感知 2 拍（约 1.6s）+ OCR + prep/LLM/gov（约 3~7s）+ pace（8~90s）+ send（3~7s）。同样主要被 pace 拉长。

### 4.5 优化顺序

1. **先调参**：联调用「快速 1~3s」；日常要快可用「标准 3~10s」；拟人档保留给风控敏感场景。
2. **缩短 kickoff**：12s → 3s，并给可见状态（P0）。
3. **压缩发送内层**：`proof` 轮询间隔/最长等待、`send_shizuku` 截图复用、IME 探针只在必要时调用（P1；需回归防错）。
4. **最后才动 OCR/提示词**：先拿到 `ocr` 与 `prep` 的均值，避免凭感觉优化。

### 5.3 待评估（P1）

- `proof` 固定等待压缩：先统计 `proof` 命中时延分布，再改轮询间隔；不能牺牲防错。

| 设置页停歇档 | 关闭 / 1 / 5 / 10 / 20 分钟 |
| 数据层合法档 | 0 / 1 / 5 / 10 / 15 / 20 分钟（0 仅停歇合法） |
| 生效方式 | `FrameDiffEngine` 每拍读取 `prefs.state.value.workMs/restMs`，下一段生效；停歇时投影常驻、暂停取帧，醒来重建差分基线 |
| 广播 | `--ei work 60 --ei rest 60`（秒；`rest=0` 不停歇；非法档忽略并打日志） |

> 注意：停歇时 `Signal.Resting` 会 toast「休息 N 分钟」，`N = restMs/60000`；1 分钟档显示 1。自动档启动首段也会走这个循环。

## 9. 本期不做，单列为下一期需求

### R1：对话结构重建与「我 / 对方」说话人归属

**问题**：当前 `FrameDiffEngine` 把 OCR/a11y 得到的文字扁平化；`OwnBubbleLocator` 只能剔除我方绿气泡，不能把剩余文字还原为「谁在什么时候说了什么」。LLM 收到的是一段无角色、无顺序的文本，回复自然缺乏逻辑。这是用户明确指出的根因，也是本期不做的边界。

**目标**

1. 把聊天页还原为有序消息列表：`[对方] 内容` / `[我] 内容`，保留时间分隔（可选）。
2. 只把「最后一条对方消息」作为待回复对象，其余作为上下文。
3. 归属置信度不足时，显式降级为「结构不可靠」提示，不伪造角色。

**技术路径（建议）**

1. **气泡检测**：不只找绿色我方气泡，还要找对方白/浅色气泡；用颜色+连通域+尺寸过滤，输出所有气泡矩形。
2. **行归属**：OCR 行盒与气泡盒的覆盖率 ≥ 阈值即归属；多行气泡按 top 排序分组。
3. **消息合并**：相邻同侧气泡合并为一条消息；时间分隔行单独成段；忽略系统 chrome/IME/引用卡片。
4. **a11y 增强**：有节点树时用 node bounds + text 直接归属；微信 a11y 黑洞场景仍以视觉为主。
5. **提示词**：把结构化对话注入 `StrategistPrompt`/`ReplyComposer`；最后一条对方消息单独标记「待回复」。
6. **置信度**：未归属行比例、气泡重叠、OCR 断行异常 → 低置信度；低置信度走现行扁平文本，避免更糟。

**验收**

- 20 张真实聊天截图 × 微信/企微：说话人归属准确率 ≥90%；我方行误判为对方 = 0。
- 同一截图重复 3 次，结构稳定；不同主题/深色模式不崩。
- LLM 回答能引用上一轮上下文（人工评分 ≥ 现状 +1 档）。
- 不回归发送链路：`out_sent`、无错会话、无重复。

**风险**

- 深色模式/自定义气泡色导致检测失败；图片、引用、语音、群聊多发言人；OCR 断行导致消息切分错误。必须保留「低置信度降级」开关。

### R2：群聊多发言人归属

在 R1 的单聊基础上扩展；需要头像/昵称区域识别与成员聚类，复杂度显著高于单聊，单列。

### R3：多会话并发与云端调度

RPA 前台/输入互斥，本期仍串行；并发需要多设备/多进程隔离，单列。

### R4：固定秒数的「秒回」SLA

受 LLM 网络、模型、拟人节奏与 RPA 防错限制；本期只给档位与分段优化，不承诺固定秒数。
