## 二、四步流程逐项对照（能力来源）

### (a) 识别对方用什么 App 发消息

已具备：

- `NotificationGate.kt`：`LISTENED_PACKAGES` = 微信 / QQ / TIM / 企业微信 / 钉钉 / 飞书 / Telegram；`parse()` 拆联系人标题 + 正文（`EXTRA_BIG_TEXT` 优先）。
- `AdvisorNotificationListener.kt`：通知 → 联系人解析 → 自动调度器入队或 `submitNotificationTurn` 后台回合；同时把 `contentIntent` 交 `ImNavigator` 内存缓存。

缺口：

1. **淘宝 / 闲鱼 / 拼多多客服 IM 不在白名单**，且通知形态是「店铺名 / 订单助手」而非「联系人名」，`parse()` 不认（B 期）。
2. 群聊折叠成「N 条新消息」、对方关闭通知、ROM 杀通知仍是感知盲区；当前靠 S1 通知为主，S2 定时巡检尚未实现。

### (a) 打开对方聊天界面 —— 已落地（v1 最大缺口已补）

- `ImNavigator.kt`：`AdvisorNotificationListener` 捕获 `contentIntent` → `remember/bindContact`
  入 LRU 缓存 → 派发时前台包名不符则 `contentIntent.send()` 拉起 → 轮询前台包名 +
  `SceneGate` 双确认；失败返回 `nav_failed:*` 并降级起草，**不盲导航**。
- `ImChatNavigator.kt`：搜索直达（拉起 IM → 点搜索 → 输入联系人名 → 点进会话）；
  a11y 不可用时走 Shizuku + 投影抽帧 + OCR/找图视觉通道；多会话调度与单目标启动共用。
- 残余缺口：通知从未捕获过 contentIntent（LRU 淘汰/通知权限关闭）时无会话钥匙；
  S2「launcher 拉起 + 会话列表巡检」路径未实现（§八、§十）。

### (b) 找到输入框与发送按钮 —— 已落地

- 聚焦步已进 `ActionDispatcher`：模式 A 先 `focusFirstEditable()`；模式 B 用
  `OcrSendLocator.focusInput()` 判输入栏形态并清空误触字符，再注入。
- 注入：`A11yInjector`（SET_TEXT/手势）与 `ShizukuInjector`（`input tap` /
  剪贴板 + `KEYCODE_PASTE`）双实现，`InjectorSelector` 按「配置 > A > B > C」选择。
- 定位：`A11ySendLocator`（节点树，取最靠下/右）与 `OcrSendLocator`（OCR/找图坐标）。
- 残余缺口：电商自绘输入框需真机采集模板后按包名微调（B 期）。

### (c) 生成「实际回复内容」—— v8 已修复

旧问题（2026-10-19 记录）：自动档直接发送最后一条 ASSISTANT 全文，即分析 + 编号建议；
`<reply>` 协议虽已写进文档，但生成端未强制执行、解码端也没有保守抽取。v8 现状：

1. **生成端硬契约**：自动档系统提示词切换为「代言者」人设（`ScreenAdvisor.ADVISOR_STYLE_AUTO`），
   `Gatekeeper.replyProtocolSection()` 规定整条输出只能有一个位于末尾的 `<reply>` 块，
   `replyContractTail()` 作为系统提示词最后一节做 recency 自检；主动开场 `AutoKickoffPrompt` 同口径。
2. **解码端确定性抽取**：`SendableDraftExtractor.extract()` 只接受 `<reply>` 块与编号建议首条；
   兼容大小写、全角、标签内空白、代码围栏、XML 转义、多块取最后、未闭合取尾段；
   分析稿特征（“建议你回复 / 回复要点 / 对方的意思… / 首先…其次 / Markdown 标题”）一律拒绝。
3. **二次代言者修复**：抽取失败时 `ReplyComposer` 用 `AuxiliaryTasks` 发起一次极轻调用，
   只输出一条纯回复；正常路径零额外调用，超时/失败返回 null。
4. **自动发送唯一出口**：陪伴窗口与多会话调度都经 `ReplyResolver` 取稿；
   起草通知复用同一抽取器（不触发修复调用）。两段都失败 → 跳过并落
   `auto_no_sendable` 台账，**绝不复用分析稿**。
5. 来源码 `reply_tag` / `reply_unclosed` / `numbered` / `composed` / `plain` 入
   `director_logs.reason`，可回放命中率。

### (d) 发送 + 循环等待

已具备：

- `SendSequence` 三步状态机（注入 → 定位发送 → 点击，每步重试；全节点/OCR 定位零硬编码坐标），
  发送后 `PostSendVerifier` 用节点树/OCR 回读上屏；成功/失败落 `director_logs(trigger=auto)` + SHA-256 指纹。
- 循环：陪伴窗口内差分引擎持续读屏 → 新回合 → Gatekeeper 双审 → 拟人延迟 8~90s → 派发；
  夜间静默/窗口上限/同联系人派发互斥/失败降级起草全齐。多会话由 `AutoSessionScheduler` 串行轮转。

缺口：

1. **无头托管未实现**：仍依赖差分引擎「看得见聊天界面」；窗口/调度器只在通知或前台可见时推进。
2. **无驻留跟进**：发出后对方迟迟不回时没有 `FollowUpWatch` 的跟进/搁置节奏。
3. **无每日总量上限与 AUTOPILOT 第四态**：当前只有单窗口上限与调度器每小时配额。

## 四、实施方案（分期）

### A 期：打通最小闭环（社交 IM 场景）—— 已基本落地

```
来信通知 ──► 后台回合 ──► ASSISTANT 全文落库
                                  │
                                  ▼
                    ReplyResolver（唯一回复出口）
                     ├─ SendableDraftExtractor：<reply>/编号确定性抽取
                     ├─ ReplyComposer：标记缺失时二次「代言者」轻调用
                     └─ 都失败 → null（落 auto_no_sendable，绝不发分析稿）
                                  │
                     Gatekeeper 自动档硬审（审的是纯回复）
                                  │
                 前台校验 ──不符──► ImNavigator（contentIntent 拉起 + 双确认）
                                  │                │ 失败 → 降级起草
                                  ▼ 符合
                 SendSequence（聚焦步 + 注入 + 定位发送）──► PostSendVerifier ──► Sent
                                  │
                 差分循环 / 多会话通知驱动等待下一回合
```

1. **`SendableDraftExtractor` + `ReplyResolver` + `ReplyComposer`（已落地，见 §二十四）**
   - 主路径：自动档提示词硬契约产出唯一 `<reply>` 块；抽取器兼容大小写/全角/空白/
     代码围栏/XML 转义/多块/未闭合；
   - 兜底：编号建议首条（仍须通过「可发送形态」判定）；
   - 修复：标记缺失时一次极轻「代言者」调用，输出仍走同一抽取器；
   - **已删除**旧的 `preamble()` 首句 / 句界截断兜底——分析句不再可能被发送；
   - 来源码 `reply_tag / reply_unclosed / numbered / composed / plain` 入台账。
2. **`ImNavigator` + `ImChatNavigator`（已落地）**
   - `AdvisorNotificationListener` 解析通知时把 `contentIntent` 存入内存 LRU
     （即取即用、不落盘），联系人解析成功后补挂 `contactId`；
   - 派发时前台包名不符 → `contentIntent.send()` → 轮询前台包名 + `SceneGate` 双确认；
   - 失败 → `nav_failed:*` 降级起草，不盲导航；
   - 多会话/单目标启动另走 `ImChatNavigator`（a11y 搜索直达或 Shizuku+视觉通道）。
3. **`PostSendVerifier`（已落地）**
   - 发送后按通道回读：A=a11y 节点树 `findText`；B=当前帧 OCR `frameContains`；
   - 多片段回退（8 字主片段 + 6 字备选）降低 OCR 假阴性；失败按 `SEND_TAP_FAILED`
     清输入框并降级，宁降级不假成功。
4. **聚焦步（已落地）**
   - 模式 A：`AssistsA11yBridge.focusFirstEditable()`；
   - 模式 B：`OcrSendLocator.focusInput()` 判输入栏形态（语音条先切键盘）→ 点击 →
     清空误触字符，再走剪贴板粘贴。

**A 期剩余（转入后续章节）**：`HeadlessAutoPilot` 无头状态机、`FollowUpWatch` 驻留跟进、
`AUTOPILOT` 第四态、向导第③步现场就绪检测、`dailySendCap`。

### B 期：电商客服面（淘宝/闲鱼/拼多多）

- `LISTENED_PACKAGES` 扩展三个电商包名；`NotificationGate.parse()` 增加「店名/订单助手」形态解析（标题=店铺名，正文含订单片段时按客服消息口径处理）；
- 电商客服界面的输入框/发送按钮 a11y 节点结构**需真机实测后**再定 SendSequence 是否需要按包名微调（如按钮文案「发送」在闲鱼是否可见于节点树）；
- 会话导航同样走 contentIntent 路径（电商通知的 contentIntent 一般直达客服会话，需验证）。

### C 期：节奏完善

- 发送后 N 分钟无回复的跟进/搁置策略（与 `routeProactive` gap 频控合流，避免双发）；
- 对方已读/输入中状态感知（a11y 节点文本嗅探，可选项，低优先）。

## 五、红线继承与新增风险

全部既有护栏不动：默认关 + 白名单 ≤5 + 拟人节奏 8~90s + 夜间静默 + 窗口上限 + Gatekeeper 双审 + 指纹对账 + 设置页风险告知二次确认。

新增风险与对策：

| 风险                                         | 对策                                                                                        |

## 六、决策记录（2026-10-19 用户确认，v8 更新）

1. **contentIntent 拉起 IM：可接受**。自动托管语义下属预期行为；失败仍降级人肉起草。
2. **纯回复生成策略（v8 定稿并落地）：`<reply>` 硬契约 + 确定性抽取 +
   代言者修复调用 + 统一出口**。

     编号建议仅保留为显式列表的兜底；
   - 标记缺失时允许**一次**极轻「代言者」修复调用（`ReplyComposer`，20s 超时、

4. 验收口径：真机微信跑 ≥10 个自动回合，`director_logs` 回放零 `WRONG_FOREGROUND`/假成功，
   外发稿全部为纯回复（无编号/分析头），`source=reply_tag` 命中率 ≥80%；
   v8 增补：`composed` 修复调用率与 `auto_no_sendable` 率可回放，零分析稿外发。

# v2 修订（2026-10-19 第二轮用户反馈）

## 八、三源感知：通知盲区的补法

用户判断正确：**通知监听不是全知**——对方关了通知权限、ROM 杀通知、群聊折叠成
「N 条新消息」（被 `GENERIC_TITLE` 过滤）、通知延迟聚合，都是盲区。

### 8.1 「联系人 → 所属 APP」映射：已存在，直接复用

contacts 档案已有 `imPackage` 字段（[ActionDispatcher.fetchImPackage](../app/src/main/java/com/verlintas/baic2/floatball/auto/ActionDispatcher.kt)
在用）。**不需要新建映射**，只需把监控面从「全局包名白名单」升级为
「**托管联系人集合 → 其绑定 app 集合**」驱动：通知按联系人过滤、巡检按 app 轮转。

### 8.2 三源评估结论

| 源                  | 可行性          | 角色               | 说明                                         |
| ------------------- | --------------- | ------------------ | -------------------------------------------- |
| S1 通知监听（现有） | ✅ 高           | **实时主路径**     | 零功耗、携带 contentIntent（拉起会话的钥匙） |
| S2 定时巡检拉起 App | ✅ 可行         | **盲区补全主路径** | 见 8.3；本项目具备 BAL 豁免条件              |
| S3 桌面图标红色泡泡 | 🔴 **不建议做** | 弃（最多旁路）     | 见 8.4，诚实评估后价值极低                   |

### 8.3 S2 定时巡检（核心增量，未实现）

- **调度载体**：复用 M2-b AlarmManager 单班闹钟（[ProactiveCheckpoint.kt](../app/src/main/java/com/verlintas/baic2/floatball/director/ProactiveCheckpoint.kt)
  同一调度面），新增「巡检班次」分支；频控按联系人分档（默认 1~4h 抖动），
  夜间静默复用 `DirectorRoutes.inQuietWindow`。
- **拉起 App 的合法性**：Android 10+ 后台启 Activity 受 BAL 限制，但本项目
  **常驻悬浮球 overlay（SAW）+ 前台服务**正属豁免路径（KeepAliveManager
  「先挂占位 overlay 再启」已有同款先例）；锁屏时跳过本轮（KeyguardManager 判断）。
- **巡检动作序列**（新组件 `ConversationListProbe`）：
  1. launcher intent 拉起 IM → 轮询前台包名 == imPackage；
  2. 会话列表页 `findText(联系人名)` 定位会话项；**微信优先走搜索直达**
     （点搜索框 → typeText 联系人名 → 结果列表点击），比长列表翻找可靠得多；
  3. 读会话项的未读角标（微信未读数是节点树里的文本节点「1」/「99+」，a11y 可读；
     需真机验证）→ 无未读 → back 退出收工；有未读 → 点进会话；
  4. 进入会话后接回合管线（读屏 → LLM → Gatekeeper → 拟人延迟 → SendSequence）。
- **成本与风控**：拉起-查看-退出动作拟人化（节奏随机化）；单轮巡检限 1 个 app；
  每日巡检次数上限；失败连续 N 次自动熔断暂停并通知用户。

### 8.4 S3 桌面角标：为什么不做

1. Android 无系统 API 读第三方 app 角标；角标由各 ROM launcher 私有绘制
   （多为自定义 View/badge drawable），**a11y 节点树大多读不到**（无 text）；
2. 即使可读也要求桌面恰在前台——后台托管场景下屏幕多半在别的 app；
3. 覆盖率与可靠性远低于 S2，投入产出不成比例。**弃**。

## 十、v2 无头全自动托管架构（目标态，未实现）

> **状态（2026-10-27）**：本节是后续目标设计。仓库内全局检索 `HeadlessAutoPilot` /
> `PatrolScheduler` / `ConversationListProbe` / `FollowUpWatch` 均为零命中；当前可用的
> 是「通知驱动 + 单会话陪伴窗口 / 多会话串行调度」，仍要求目标聊天页可见，尚未做到

用户口径明确：**自动模式不弹分屏、不弹叠加窗，纯后台循环**：
监控 → 触发（通知/定时）→ 自动打开 App → 输入实际回复 → 驻留跟进一段时间 →
暂停 → 下一轮触发。LLM 分析全程后台。

### 10.1 形态定义

- **Headless 托管**为自动档的新运行形态，取代陪伴窗口的前台依赖：
  分屏面板（TranscriptView）**不挂载**，悬浮球保持常驻（它同时是 SAW 豁免的
  载体与用户手动介入的入口）；差分引擎照常由服务拉起，只是无 UI 观察——
  「通知后台回合」已证明不开分屏也能跑完整回合管线，无头化是同一形态的扩展。
- 截屏通道：跟进期用 **a11y `captureScreen()`**（API 30+，免授权、无系统弹窗、
  无投影指示灯；服务配置 `canTakeScreenshot` 已开），不再依赖 MediaProjection
  「拍完即关」。悬浮球在帧内的干扰由既有 OcrNoiseFilter/掩膜消化（连续参谋
  模式悬浮球常驻读屏已是既有先例）。

### 10.2 状态机与新组件

```
HeadlessAutoPilot 状态机：
  SUSPENDED(默认) ──S1通知/S2巡检──► NAVIGATING ──前台+SceneGate.CHAT──► CONVERSING

                                                                           │成功
                                                                           ▼
                                                                     FOLLOWUP(驻留跟进)
                                       用户接管/超时/静默 ◄──(对方回复→下一回合)
                                       ▼

```

用户原始意图（2 次连续间隔 10 分钟、发现消息→自动监控 10 分钟→停止→循环）方向正确；
为同时满足**防杀、省电、防风控**三个目标，工程化为三件套（全部参数化）：

1. **自适应退避（防风控/省电核心）**：巡检间隔不是固定值，按「活跃度」分档动态调节——
   - 平静期（连续 K 轮未发现新消息）：间隔逐轮退避 `30min → 1h → 2h → 4h`（封顶，随机抖动 ±30%）；
   - 活跃期（本轮发现未读/刚完成会话）：下轮间隔收紧至 **10 分钟**（用户口径，参数可调），
     连续活跃上限 N 轮（默认 6 轮≈1 小时）后强制回退避曲线——**避免整天 10 分钟一次
     被平台风控盯上**；
   - 夜间静默（quiet 口径）完全停巡，静默结束不补巡（下一正常检点即可）。
2. **会话驻留窗（FollowUpWatch 时长语义）**：检测到新消息/发送成功后进入驻留监控
   （a11y 截图轮询为主、MediaProjection 录屏兜底——用户口径「无障碍模式+录屏兜底」采纳；
   a11y 通道异常（API<30 或截图连续失败）时才走投影授权）：
   - 对方持续回复 → 多回合循环（每回合 Gatekeeper→拟人延迟→发送）；
   - 驻留上限 10 分钟（参数可调）或连续 3 分钟无新消息即提前退出；
   - 退出动作：back 离开会话（回原界面）→ 挂起等下一触发。比固定 10 分钟更省电、
     更拟人（聊完即走）。
3. **链式闹钟（防杀/省电载体）**：不用长驻轮询，每轮检点完成即排下一次 one-shot
   `setExactAndAllowWhileIdle`（复用 M2-b 单班闹钟面，随机抖动）；进程被杀后由
   KeepAliveManager 既有三级降级复活 + 闹钟重排；锁屏期跳过拉起（KeyguardManager），
   只保留 S1 通知通道（通知监听不亮屏也能跑）。

参数表（全部进设置页，`AdvisorPrefs`）：

| 参数                   | 默认  | 说明                       |
| ---------------------- | ----- | -------------------------- |
| patrolBaseIntervalMs   | 30min | 平静期起始间隔             |
| patrolBackoffMaxMs     | 4h    | 退避封顶                   |
| patrolActiveIntervalMs | 10min | 活跃期间隔（用户口径）     |
| patrolActiveMaxRounds  | 6     | 活跃期连续轮数上限         |
| followUpWindowMs       | 10min | 会话驻留窗时长             |
| followUpIdleMs         | 3min  | 驻留内无新消息提前退出阈值 |
| dailySendCap           | 20    | 每日自动发送上限           |
| autoWhitelistMax       | 3     | 托管白名单上限             |

## 十七、R1 集成纪律四条（v4 用户指令）

### 17.1 a11y 执行面全面切换 assists 封装

用户事实判断成立：微信新版（首页/聊天/小程序/H5 混合页）节点文本稀疏且动态，
本方 `findText` 纯文本包含匹配 + `screenText` 扁平串，对最新微信的识别力不足；
assists 的结构化查询（按 resource-id/className/可点击父链的 `findById`/`findByTags`、
节点树 JSON、节点直接动作）才是能稳定解析微信对象树的通道。

落位：

- **保留 `AccessibilityBridge` 接口契约**（SendSequence/AgentLoop/tools 全部调用方零改动），
  **实现内部整体切换**：新建 app 层 `floatball/auto/AssistsA11yBridge.kt`，把
  `findText/screenText/tap/typeText/pressKey/...` 的实现委托给 `AssistsCore`
  （继承合体后全局实例可用）；`DeviceImplModule` 的 `@Binds` 换绑一行
  （与 F4 换绑合并为同一处 `[upstream-touch]`）；
- `TextNode` 语义保持（text+bounds），内部由 assists 节点树换源——上游调用方
  （tools/ui_control 等）自动受益于更强的微信解析力，无需各自改代码；
- 首选定位链升级为：**resource-id/描述精确匹配（assists 选择器）→ 文本包含匹配
  （现语义保留作兜底）→ OCR → 找图**（与 §6 RPA 找图链汇合）。

### 17.2 三模执行面（v5 修订：免 a11y 也要全自动托管）

用户明确需求：**无 a11y 时也要能全自动托管**。感知环无障碍成立（录屏抽帧+OCR+找图
能定位输入框/发送按钮坐标），缺的只是「坐标→点击」的注入通道。Android 平台注入
通道有且仅有三条：a11y 手势 / root / shell（adb-Shizuku）。据此执行面修订为三模：

| 模式                                | 感知面                              | 执行面                                           | 能跑什么                    |
| ----------------------------------- | ----------------------------------- | ------------------------------------------------ | --------------------------- |
| **A：a11y 模式**                    | a11y 树（assists）+ a11y 截图 + OCR | 节点动作/手势/SET_TEXT/粘贴                      | 参谋 + 全自动托管（现路线） |
| **B：Shizuku 模式（免 a11y 托管）** | **录屏抽帧 + OCR + 找图**           | **shell `input tap/text` 注入**（Shizuku shell） | 参谋 + **全自动托管**       |
| **C：纯感知模式**                   | 通知监听 + 录屏抽帧 + OCR + 找图    | 无（剪贴板代拟 + 跳转人肉粘贴）                  | 参谋 + 起草档               |

核心设计：**`InputInjector` 执行通道抽象**（floatball/auto，接口 + 双实现）：

- `A11yInjector`：现 SendSequence 底座（节点定位+手势/SET_TEXT）；
- `ShizukuInjector`：Shizuku shell 执行 `input tap x y` / 注入文本；SendSequence
  的「定位」改由录屏抽帧+OCR+找图产出的**坐标**驱动，「注入/点击」由 injector 执行——
  **定位与执行解耦后，三步状态机底座两种通道共用**；
- 选择逻辑：优先用户配置的通道；未配置时按可用性降级 A→B→C（C 不算「托管」，
  自动挂起草档）。

Shizuku 通道要点：

- **授权一次、长期免 a11y**：Android 11+ 「无线调试」可在手机端自启 Shizuku
  （无需电脑、无需 root）；本项目 device/impl 已有 Shizuku 依赖；
- **中文注入两条子路径**（shell `input text` 不支持 Unicode）：
  ① `cmd clipboard`（shell 权限可写剪贴板，13+）写入纯回复 → `input keyevent KEYCODE_PASTE`；
  ② 辅助 IME 广播注入（ADBKeyboard 同款机制，安装本方内置 IME，用户切一次输入法）。
  R1 验收时实测择优，默认 ①；
- **风控加分**：`input tap` 在系统输入层注入（InputReader 虚拟设备），目标 app
  侧无 a11y 服务可检测、无 a11y 节点查询痕迹——**比 a11y 模式更不易被微信识别**，
  正面回应「开无障碍可能被封杀」的顾虑；
- **检测面评估（2026-10-20）**：① 「USB/无线调试已开启」开关 app 可读但属弱信号
  （开发者模式普遍，「开着」≠「在被用」）；② Shizuku/adb **活跃会话对第三方 app
  不可知**（无公开 API/广播/日志）；③ 注入事件带虚拟设备 id 理论可查，主流 IM
  未见实际采用；④ 真正暴露面是行为模式（秒回/坐标机械重复）——拟人节奏、退避、
  上限护栏照常覆盖。结论：Shizuku 通道检测面比 a11y 小一个量级；
- **可用性代价**：无 root 时手机重启后 Shizuku server 需用户重新拉起（无线调试
  一键自启，不需电脑）——托管/巡检遇 Shizuku 断连自动降级 C 档起草并通知用户；
  root 用户可开机自启消除该成本；
- 免 a11y 模式下的巡检/导航同样成立：launcher 拉起是普通 startActivity；会话
  列表未读检测由「录屏抽帧+OCR/找图」替代 a11y 树（更慢但可跑）；锁屏跳过逻辑不变；
- 代价（设置页明示）：录屏授权弹窗 + 状态栏指示灯（可先静默感知后集中执行窗口），
  找图定位比 a11y 树慢（ROI 优先缓解）。

### 17.3 帧源阶梯（OpenCV 与 OCR 的输入统一）

RPA 文档原设计「只用 a11y 截图」按用户指令修订为**帧源接口双通道**：

```
FrameSource 阶梯：a11y captureScreen（API30+，免授权，首选）
                 → MediaProjection 抽帧（免 a11y 模式 / a11y 截图连续失败时兜底）
                 → ImageMatcher(image) / OcrProvider(image)
```

- `ImageMatcher` 只认 `FrameSource` 产出的 Bitmap，不关心来源——同一套找图
  逻辑在两种模式下复用；
- 免 a11y 模式的录屏帧源 **采用 assists-mp**（2026-10-20 用户决策：mp 带入、
  不动 assists 代码）——它是 assists-opcv 的原生配套帧源，opcv→mp 链路闭合
  零裁剪；自家 `FloatCaptureBridge` 保留于屏幕参谋投影读屏（既有链路不动），
  两套投影各守领地：**参谋=自家链，自动托管找图=assists-mp**；
- assists-mp 的授权中转（MediaProjection 必须由 Activity 发起，铁律 §8.2）与
  Android 14+ 一授权一投影的兼容性在 R1 第 5 步实测；抽帧节流复用
  FrameDiffEngine 节奏参数（省电）；
- 录屏兜底的代价（授权弹窗、状态栏指示灯、Android 14+ 一授权一投影）在
  设置页文案与风险告知中明示。

## 二十四、确定性回复通道 v8（2026-10-27）

> 本节回答用户提出的核心问题：**如何让 LLM 一定输出一段确定的回复文字？如何让这段
> 文字一定被特定标记包围，从而方便程序提取？有没有比「标记 + 提取」更好的方式？**

### 24.1 先把问题说清楚

用户观察到的事实成立：此前自动档把模型输出直接当发送正文，而模型的默认人格是
「好参谋」——它输出的是意图分析 + 回复建议，不是一条可发送的话；约定的 `<reply>`
标记既没有在生成端被强制，也没有在解码端被严格识别。

这里有两个不同层次的问题，必须分开解决：

1. **生成端**：怎样让模型「愿意且记得」把唯一回复写进标记块？
2. **解码端**：模型没照做、写错格式、或块里仍夹着分析时，程序怎样保证不发错？

**工程上不存在 100% 的 prompt 保证**。模型是概率系统，任何提示词都可能被忽略或
被更早的长指令带偏。因此 v8 不追求「一句话命令模型」，而是做四层闭环：

```
生成端硬契约 → 解码端确定性抽取 → 失败时一次代言者修复 → 统一出口 + 保守降级
```

**一句话答案**：在系统提示词最后一段明确「整条输出只能有一个位于末尾的 `<reply>`
块，忘记标记 = 本条作废」；程序端不信任模型，抽取不到就再叫一次「代言者」写一条，
仍然失败就不发。这样即使模型不听话，也不会把分析稿发出去。

四层里任何一层失败，最终结果都是「不发」或「降级起草」，**永远不会退回分析稿**。
这就是「确定性」的真正来源：不是相信模型，而是不相信模型也能保证结果可控。

### 24.2 第一层：生成端硬契约（已落地）

落位：`Gatekeeper.replyProtocolSection()`、`replyContractTail()`、
`ScreenAdvisor.ADVISOR_STYLE_AUTO`、`AutoKickoffPrompt`。

关键做法不是「请用 `<reply>` 标记」这种软建议，而是把它写成**可判定作废的硬契约**：

1. **切换人格**：自动档把系统提示词的人设从「参谋」切成「代言者」——首要交付物是
   一条用户本人能直接发出去的话；分析最多一句，不写报告、不列建议清单。
2. **唯一块 + 末尾 + 块后无字符**：整条输出必须包含且只包含一个 `<reply>` 块，
   并放在最后；块外只允许一到两句判断，不得再给第二版候选。
3. **明确失败语义**：「忘记写标记 = 本条回复作废，系统不会发送」——让模型知道
   格式不是装饰，而是发送的必要条件。
4. **few-shot 示例**：给一条真实口语风格的完整示例，降低模型自由发挥空间。
5. **recency 自检**：`replyContractTail()` 作为整条系统提示词的最后一节，要求模型
   输出前自检「末尾是否恰好有一个 `<reply>` 块」；放在最后是因为模型对末尾指令
   的遵守率通常更高。
6. **主动开场同口径**：`AutoKickoffPrompt` 也要求以 `<reply>` 收口，避免「主动开场」
   变成另一套格式。

修复调用（`ReplyComposer`）则使用更窄的独立提示词：只有「代言者」一个任务、
输出只有一个块、temperature=0.7、maxTokens=220。它不复用主回合的长上下文，
从源头减少人格干扰。

### 24.3 第二层：解码端确定性抽取（已落地）

落位：`SendableDraftExtractor.extract()`（纯函数、零 LLM、JVM 可单测）。

程序不能假设模型一定按格式输出，所以抽取器做的是「宽容识别 + 严格判定」：

| 模型可能的写法                                   | 抽取器处理                                     |
| ------------------------------------------------ | ---------------------------------------------- |
| `<reply>…</reply>`                               | 标准命中，来源码 `reply_tag`                   |
| `<REPLY>…</Reply>`、`＜ reply ＞…＜／reply＞`      | 大小写/全角/标签内空白归一化                   |
| `&lt;reply&gt;…&lt;/reply&gt;`                   | XML 转义还原                                   |
| 代码围栏包裹                                     | 去围栏后识别                                   |
| 多个 `<reply>` 块                                | 从后往前取第一个通过形态判定的块               |
| 只有 `<reply>` 没有 `</reply>`                   | 取开标记之后的剩余文本，来源码 `reply_unclosed` |
| 显式编号建议列表（≥2 条连续编号）                | 取首条，来源码 `numbered`                      |
| `<reply>建议你这样回复：……</reply>`              | **拒绝**（块内有分析元话语）                   |
| 长文、列表、Markdown 标题、多句分析              | **拒绝**                                       |

形态判定 `looksLikeReply()` 是第二道闸：长度上限（默认 800 字，随长度档放宽）、
句数上限 4 句、分析特征词（「建议你回复」「回复要点」「对方的意思可能是」
「首先…其次」「分析：」等）、Markdown 标题、占位符，任一命中即判 null。
**v8 已删除旧的 `preamble()` 首句/句界截断兜底**——那种「从分析稿里切一句」
的做法正是把分析当回复发出的根源。

### 24.4 第三层：一次「代言者」修复调用（已落地）

落位：`ReplyComposer` + `ReplyComposeSource` 接口 + `ReplyModule` 绑定。

- **只在主回合抽不到合法回复时触发**，正常路径零额外调用；
- 输入只有：对方最新来信（截断 400 字）+ 参谋分析（截断 1200 字，标注「仅背景」）
  + 近期已发（防复读）+ 目标字数；
- 输出仍走同一套抽取器，先 `extract()`，再 `extractPlain()`（仅修复通道允许
  「模型忘写标记、但整条就是一段短回复」的极窄兜底）；
- 20s 超时、失败返回 null；来源码统一为 `composed`；
- 修复稿仍要过 Gatekeeper 双审，不会因为「是修复调用产的」而跳过审查。

### 24.5 第四层：统一出口 + 保守降级（已落地）

落位：`ReplyResolver`（两条自动发送路径）+ `SendableDraftExtractor`（起草档复用）：

| 调用方                       | 场景                         | 取不到回复时                       |
| ---------------------------- | ---------------------------- | ---------------------------------- |
| `CompanionWindowController`  | 单会话陪伴窗口逐回合         | `auto_no_sendable` 台账 + 跳过本轮 |
| `AutoSessionScheduler`       | 多会话通知驱动串行调度       | 同上                               |
| `AdvisorNotificationListener`| 起草通知（人肉一键发送）     | 直接复用同一抽取器（等同 `allowCompose=false`）；抽不到展示全文供编辑 |

统一出口的意义是**自动发送路径的纪律只有一条**：会「自动把文字发出去」的两条路径
（陪伴窗口、多会话调度）都必须经过 `ReplyResolver`；分析全文只作为落库素材和修复
调用的背景，**结构上不可能直接进入发送通道**。起草通知不触发修复调用，但复用同一
抽取器与形态判定，因此也不会把分析稿当作「纯回复」展示给用户。来源码
（`reply_tag` / `reply_unclosed` / `numbered` / `composed` / `plain`）写入
`director_logs.reason`，可回放命中率。

### 24.6 为什么是「标记 + 抽取」，而不是别的

| 方案                              | 语法确定性 | 语义确定性 | 兼容/成本                                           | 结论                     |
| --------------------------------- | ---------- | ---------- | --------------------------------------------------- | ------------------------ |
| **`<reply>` 标记 + 形态判定**     | 高（可容错）| 高（拒绝分析）| 零/低；所有 Provider 通用，流式可用                 | ✅ 当前主路径            |
| 只要求「直接输出回复」            | 低         | 低         | 便宜，但无法区分分析句与回复句                      | ❌ 已证明会漏分析        |
| JSON Schema `response_format`     | 最高       | 仍需形态判定 | 需改 `ChatRequest` 与 OpenAI/Gemini/Anthropic 三 Provider；当前抽象不支持 | 🔜 R2 可选，不是必需     |
| 强制 tool call（`send_reply`）    | 最高       | 仍需形态判定 | 各 Provider 工具协议差异大；同样要语义校验          | 🔜 R2 可选               |
| assistant prefill（预填 `<reply>`）| 高         | 中         | 部分 Provider 支持，当前抽象未暴露                  | 🔜 R2 可选               |
| constrained decoding / grammar     | 最高       | 仍需形态判定 | 仅自托管推理可控，云端 API 不适用                   | ⛔ 不作为产品方案        |
| 双通道（军师分析 + 代言者每次都单独生成） | 高   | 高         | 每回合固定两次 LLM，成本/延迟翻倍                   | 🟡 修复调用的常驻化版本  |

结论：

- **标记法仍然是当前最优解**：它不依赖某家 Provider 的结构化输出能力，流式下也能
  先落全文、回合结束后再抽取；成本几乎为零，且能与 Gatekeeper 的文本审查共用同一份稿。
- **但「标记包围」只解决语法，不解决语义**。真正防止「`<reply>` 里写分析」的是
  形态判定与 Gatekeeper，不是标记本身。
- **更强的结构化输出值得做，但只是下一层保险**：即使 JSON Schema 保证 `reply` 字段
  一定存在，也不能保证字段内容不是「建议你这样回复」。因此 R2 的正确做法是
  `response_format` 产出 JSON → 取 `reply` 字段 → **仍然过同一套形态判定与审查**，
  而不是用结构化输出替代形态判定。
- **assistant prefill 对开源/兼容网关有效，但不是所有 Provider 都支持**，只能作为
  可选增强，不能作为唯一路径。

### 24.7 对「AI 代理没有真正扮演角色」的回应

五岗不是五个常驻聊天的 LLM，而是同一条回合管线上的五个职责位：

| 岗位       | 职责                                   | v8 落点                                             |
| ---------- | -------------------------------------- | --------------------------------------------------- |
| 哨官 Sentry | 发现来信、解析联系人、触发回合         | `AdvisorNotificationListener` / `NotificationGate`  |
| 军师 Strategist | 判断意图、策略、情绪与手段库        | `ScreenAdvisor` 的策略/许可/情绪段                  |
| 代言者 Responder | **产出唯一一条可发送回复**         | 自动档人设 + `<reply>` 契约 + `ReplyComposer`       |
| 审查官 Gatekeeper | 红线、复读、金额/承诺/隐私/超阶段拦截 | `Gatekeeper` 双审，审的是纯回复                     |
| 档案官 Archivist | 台账、来源码、指纹、失败原因回放     | `director_logs`（`draftSource` / `auto_no_sendable`）|

v8 之前，Responder 的交付物实际上是「参谋分析」，所以用户感觉不到它在扮演角色；
v8 把它的交付物改成一条可直接发送的文本，并把「参谋分析」降级为背景素材。这是
「让代理真正做事」的第一处实质变化。还缺的是：多会话调度不能主动发起、没有驻留
跟进、没有独立 App 集合与每日上限——这些属于 §十/§十一的执行面增量，不是回复
通道本身的问题。

### 24.8 验收指标（真机回放）

| 指标                     | 口径                                                       | 目标        |
| ------------------------ | ---------------------------------------------------------- | ----------- |
| 标记命中率               | `source=reply_tag/reply_unclosed` ÷ 自动发送回合           | ≥ 80%       |
| 修复调用率               | `source=composed` ÷ 自动发送回合                           | 首版 ≤ 20%，随提示词优化下降 |
| 无可发送回复率           | `auto_no_sendable` ÷ 触发回合                              | ≤ 5%，且每条可回放原因 |
| 分析稿外发               | 外发正文含分析特征词/编号/Markdown 的条数                  | **0（硬红线）** |
| 复读拦截                 | Gatekeeper 近 3 条纯回复重复命中                           | 全部拦截    |
| 发送假成功/重复发送      | `PostSendVerifier` 失败与同指纹重复                        | **0（硬红线）** |
| 单测回归                 | `SendableDraftExtractorTest` 19 项 + `ReplyResolverTest` 5 项 | 全绿        |

### 24.9 后续增强（R2，按需）

1. **结构化输出**：`ChatRequest` 增加 `responseFormat`（JSON Schema），OpenAI-compatible
   先落地；`{ "reply": "..." }` 解析后仍过 `looksLikeReply()` 与 Gatekeeper。
2. **强制 tool call**：为支持的 Provider 暴露 `send_reply(text)` 工具并 `tool_choice=required`；
   不支持的 Provider 继续走标记协议。
3. **assistant prefill**：对支持的网关预填 `<reply>`，让模型从标记内部续写；失败仍回退。
4. **来源码可视化**：主页/设置页展示近 7 天 `reply_tag/composed/numbered/no_sendable`
   分布，作为提示词迭代依据。
5. **修复调用预算**：按通道/联系人配置是否允许修复调用，避免弱网/高延迟下拖住队列。
