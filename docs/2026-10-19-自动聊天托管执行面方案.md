# 自动聊天托管执行面方案（2026-10-19）

> 目标：让「自动」模式真正跑通用户描述的四步闭环——**识别来信 App → 打开对方聊天界面 → 把「实际回复」（非分析稿）注入输入框 → 点发送 → 循环等待**。
> 本文只做现状对照与方案设计，未动任何代码；批准后实施。

---

## 一、结论先行

| 用户步骤                 | 现状          | 结论                                                                                                               |
| ------------------------ | ------------- | ------------------------------------------------------------------------------------------------------------------ |
| (a) 识别来信 App         | ✅ 已具备     | 通知白名单 7 个社交 IM + 联系人解析 + 后台回合，全通                                                               |
| (a) **打开对方聊天界面** | ❌ **缺失**   | 没有「拉起 IM 会话」组件；派发时只校验前台包名，不在就降级人肉                                                     |
| (b) 找到输入框/发送按钮  | 🟡 基本具备   | `typeText`(焦点/首个可编辑节点) + `findText("发送"/"send")` 已通；缺显式「聚焦输入框」步                           |
| (c) 生成**实际回复**     | 🔴 **走样**   | 自动档草稿 = 最后一条 ASSISTANT 气泡**全文（分析+编号建议）**，无确定性「纯回复抽取」通道                          |
| (d) 点发送 + 循环等待    | 🟡 具备但受限 | 三步状态机+重试+指纹对账+拟人节奏+差分循环都在；但**人一离开聊天界面，自动档即停摆**（全部 WRONG_FOREGROUND 降级） |

**一句话：感知面（通知/读屏）与治理面（硬审/节奏/台账）已经完整，缺的是「执行面」三块——会话导航、纯回复通道、发送确认。**

## 二、四步流程逐项对照（能力来源）

### (a) 识别对方用什么 App 发消息

已具备：

- [NotificationGate.kt](file:///e:/_android_work/NovaBAIC/app/src/main/java/com/verlintas/baic2/floatball/director/NotificationGate.kt)：`LISTENED_PACKAGES` 白名单 = 微信 / QQ / TIM / 企业微信 / 钉钉 / 飞书 / Telegram；`parse()` 拆联系人标题 + 正文（`EXTRA_BIG_TEXT` 优先）。
- [AdvisorNotificationListener.kt](file:///e:/_android_work/NovaBAIC/app/src/main/java/com/verlintas/baic2/floatball/director/AdvisorNotificationListener.kt)：通知 → 联系人解析（未建档静默忽略）→ `submitNotificationTurn` 后台回合。

缺口：

1. **淘宝（com.taobao.taobao）/ 闲鱼（com.taobao.idlefish）等电商客服 IM 不在白名单**，且其通知形态是「店铺名 / 订单助手」而非「联系人名」，`parse()` 直接不认。
2. **`sbn.notification.contentIntent`（点通知直达会话的 PendingIntent）完全没用上**——这是 Android 生态里打开指定聊天最可靠的钥匙。

### (a) 打开对方聊天界面 —— 当前最大的洞

- [ActionDispatcher.kt](file:///e:/_android_work/NovaBAIC/app/src/main/java/com/verlintas/baic2/floatball/auto/ActionDispatcher.kt) `SendSequence.run()` 第一步：`bridge.foregroundPackage() != imPackage` → `REASON_WRONG_FOREGROUND` → 降级起草通知。**它只查门是否开着，从不敲门。**
- 也就是说：通知来的消息 → 后台回合生成了草稿 → 派发时人不在微信里 → **必然降级人肉**。陪伴窗口的「自动」事实上只在「用户本来就停在聊天界面」时才真正自动发——与用户期望的「自动托管聊天」不符。

### (b) 找到输入框与发送按钮

已具备（[AndroidAccessibilityBridge.kt](file:///e:/_android_work/NovaBAIC/device/impl/src/main/kotlin/com/verlintas/baic2/device/impl/a11y/AndroidAccessibilityBridge.kt) + SendSequence）：

- `typeText`：`findFocus(FOCUS_INPUT)` → 兜底全窗口 `firstEditable()`，`ACTION_SET_TEXT` 注入，失败重试一次。
- `findText("发送"/"send")`：text/contentDescription 包含匹配 + 尺寸异常过滤 + **取最靠下、其次最靠右**（IM 发送按钮恒在底部输入栏右端）。微信发送按钮仅在输入框非空时出现，现有「先注入再找发送」的顺序恰好适配。

缺口：

- 没有显式「先点输入框聚焦」步——依赖焦点恰好在输入框、或界面只有一个可编辑节点。淘宝客服页（顶部还有搜索框类节点）有误聚焦风险。

### (c) 生成「实际回复内容」—— 方案走样点

事实链（已核实）：

1. 回合落库的 ASSISTANT 消息 = LLM 可见输出**全文**：分析引言 + 「1./2./3.」编号建议（[ScreenAdvisor.kt](file:///e:/_android_work/NovaBAIC/app/src/main/java/com/verlintas/baic2/floatball/ScreenAdvisor.kt) L2232-2242）。
2. 自动档草稿 = `messages.lastOrNull { it.role == ASSISTANT }.content`（[CompanionWindowController.kt](file:///e:/_android_work/NovaBAIC/app/src/main/java/com/verlintas/baic2/floatball/auto/CompanionWindowController.kt) L439-442）——**整条分析气泡**。
3. 唯一的「口径约束」是 [Gatekeeper.autoForbiddenSection()](file:///e:/_android_work/NovaBAIC/app/src/main/java/com/verlintas/baic2/floatball/director/Gatekeeper.kt) L234-239：只追加红线（不报价/不代决定…），**并未要求「只输出一条可直接发送的纯回复、禁止分析与编号」**。
4. 兜底是 Gatekeeper 双审（确定性三查+四类词表+轻 LLM 审），超长有句界截断——但这是「事后修剪」，不是「事前就生成对的东西」。

这与用户的判断完全一致：现在发出去的是「参谋的分析稿」，不是「实际回复」。

可复用的既有能力：[ReplySuggestions.kt](file:///e:/_android_work/NovaBAIC/app/src/main/java/com/verlintas/baic2/floatball/advisor/strategy/ReplySuggestions.kt) 已能从参谋输出解析编号建议（`parse()`）与剥引言（`preamble()`）——纯函数、已单测，抽取器可直接建在它上面。

### (d) 发送 + 循环等待

已具备：

- 发送三步状态机（定位输入 → 注入 → 找发送 → 点击，每步一次重试，全节点树定位零硬编码坐标）；成功/失败落 `director_logs(trigger=auto)` + SHA-256 指纹对账。
- 循环：陪伴窗口内差分引擎持续读屏 → 对方回复引起画面变化 → 新回合 → 硬审 → 拟人延迟 8~90s → 派发。夜间静默/窗口上限/同联系人派发互斥/失败降级起草，全齐。

缺口：

1. **脱离前台即停摆**（见 (a)）——循环强依赖「差分引擎看得见聊天界面」。
2. **无发送后确认**：`tap` 返回成功即记 `Sent`，不验证消息真的上屏；误判成功会让循环在错误状态上继续。
3. 无「发出后对方迟迟不回」的跟进/搁置节奏（M2-b `routeProactive` 的 gap 频控部分覆盖主动发起新话头，但不是回复跟进语义）。

## 四、实施方案（分期）

### A 期：打通最小闭环（社交 IM 场景）

```
来信通知 ──► 后台回合（现有） ──► ASSISTANT 全文落库（现有）
                                        │
                                        ▼
                     SendableDraftExtractor 产出「纯回复」
                                        │
                          Gatekeeper 自动档硬审（现有，审的是纯回复）
                                        │
                     前台校验 ──不对──► ImNavigator（contentIntent 拉起会话）
                                        │            │ 仍失败 → 降级起草
                                        ▼ 对
                     SendSequence（+聚焦步） ──► PostSendVerifier ──► Sent
                                        │
                     差分循环等待对方回复（现有）
```

1. **SendableDraftExtractor**（核心，纯函数，零额外 LLM 调用）——标记协议 + 三级兜底链：
   - **主路径：`<reply>` 标记协议**（用户决策 2026-10-19）。自动档系统提示词约定模型输出格式：
     `…（可自由分析的参谋内容）…` + **`<reply>一条可直接发送的纯回复正文</reply>`**。
     提取机制与上游 `<plan>` 块剥离同构（[PlanStreamFilter](file:///e:/_android_work/NovaBAIC/app/src/main/java/com/verlintas/baic2/floatball/advisor/strategy/PlanStreamFilter.kt)
     的 feed/endStream 模式）：分屏照常展示全文（reply 块可折叠展示），落库/发送取 reply 块。
     选 XML 风格标记而非中文字面记号（「回复开始/回复结束」）的理由：不与正文文本冲突、
     流式可增量剥离、未闭合/缺失可确定性检测降级。
   - **兜底一**：标记缺失/未闭合 → `ReplySuggestions.parse()` 命中编号建议 → 取第一条；
   - **兜底二**：仍无 → `preamble()` 引言首句 / `answerTargetChars` 句界截断；
   - 产出带 `source`（reply_tag / numbered / truncated）入台账 reason，回放可见草稿来源与兜底触发率；
   - 双保险：提示词规约段同时要求「reply 块外不做任何『这样回复会…』式的自评展开」，
     从源头减少需要修剪的稿子。
2. **ImNavigator**
   - 首选路径：`AdvisorNotificationListener` 在解析通知时把 `sbn.notification.contentIntent` 存入内存中的会话导航缓存（**即取即用，不落盘不序列化**，与通知文本同隐私红线），key = `imPackage|contactId`；
   - 派发时前台包名 ≠ imPackage → `contentIntent.send()` 拉起 → 轮询等待（上限约 5s）前台包名==imPackage 且 `SceneGate` 判 CHAT → 放行 SendSequence；
   - 拉起失败/超时 → `REASON_NAV_FAILED` 降级起草（人肉档现状不变）。
   - 兜底路径（launcher intent + a11y 找会话标题点击）**本期不做**——盲导航错进会话的风险大于收益，等 contentIntent 路径实测覆盖不足再评估。
3. **PostSendVerifier**
   - 发送后 1s 用 `findText(草稿前 8~12 字)` 验证消息节点已上屏（消息气泡文本会在节点树中出现）；验证失败按 `SEND_TAP_FAILED` 处理并清输入框残留，台账记失败——宁降级不假成功。
4. **聚焦步**：`typeText` 前若 `editableFocused()==false`，先对首个可编辑节点 `tap` 其中心聚焦，再注入。

### B 期：电商客服面（淘宝/闲鱼/拼多多）

- `LISTENED_PACKAGES` 扩展三个电商包名；`NotificationGate.parse()` 增加「店名/订单助手」形态解析（标题=店铺名，正文含订单片段时按客服消息口径处理）；
- 电商客服界面的输入框/发送按钮 a11y 节点结构**需真机实测后**再定 SendSequence 是否需要按包名微调（如按钮文案「发送」在闲鱼是否可见于节点树）；
- 会话导航同样走 contentIntent 路径（电商通知的 contentIntent 一般直达客服会话，需验证）。

### C 期：节奏完善

- 发送后 N 分钟无回复的跟进/搁置策略（与 `routeProactive` gap 频控合流，避免双发）；
- 对方已读/输入中状态感知（a11y 节点文本嗅探，可选项，低优先）。

## 五、红线继承与新增风险

全部既有护栏不动：默认关 + 白名单 ≤5 + 拟人节奏 8~90s + 夜间静默 + 窗口上限 + Gatekeeper 双审 + 指纹对账 + 设置页风险告知二次确认。

新增风险与对策：

| 风险                                         | 对策                                                                                       |
| -------------------------------------------- | ------------------------------------------------------------------------------------------ |
| ImNavigator 拉起 IM = 用户可见的「自己动了」 | 仅自动档白名单联系人在窗口期发生；台账全程可回放；设置页风险告知文案补充说明               |
| contentIntent 缓存误路由（过期/指向错会话）  | key 绑定 imPackage+contactId；send 后校验前台包名+SceneGate 双确认；不落盘即取即用         |
| 纯回复抽取抽错段（把分析当回复发出）         | 抽取器带 source 入台账；Gatekeeper 硬审照常把关口径；A 期验收含「连续 N 回合零分析稿外发」 |
| 发送假成功                                   | PostSendVerifier 节点树回读                                                                |
| 平台风控（微信 ToS）                         | 拉起-发送-停留行为拟人化（已有节奏）；不做的比做的多——不加批量、不加高频、不跨联系人轮询   |

# v2 修订（2026-10-19 第二轮用户反馈）

## 八、三源感知：通知盲区的补法

用户判断正确：**通知监听不是全知**——对方关了通知权限、ROM 杀通知、群聊折叠成
「N 条新消息」（被 `GENERIC_TITLE` 过滤）、通知延迟聚合，都是盲区。

### 8.1 「联系人 → 所属 APP」映射：已存在，直接复用

contacts 档案已有 `imPackage` 字段（[ActionDispatcher.fetchImPackage](file:///e:/_android_work/NovaBAIC/app/src/main/java/com/verlintas/baic2/floatball/auto/ActionDispatcher.kt)
在用）。**不需要新建映射**，只需把监控面从「全局包名白名单」升级为
「**托管联系人集合 → 其绑定 app 集合**」驱动：通知按联系人过滤、巡检按 app 轮转。

### 8.2 三源评估结论

| 源                  | 可行性          | 角色               | 说明                                         |
| ------------------- | --------------- | ------------------ | -------------------------------------------- |
| S1 通知监听（现有） | ✅ 高           | **实时主路径**     | 零功耗、携带 contentIntent（拉起会话的钥匙） |
| S2 定时巡检拉起 App | ✅ 可行         | **盲区补全主路径** | 见 8.3；本项目具备 BAL 豁免条件              |
| S3 桌面图标红色泡泡 | 🔴 **不建议做** | 弃（最多旁路）     | 见 8.4，诚实评估后价值极低                   |

### 8.3 S2 定时巡检（核心增量）

- **调度载体**：复用 M2-b AlarmManager 单班闹钟（[ProactiveCheckpoint.kt](file:///e:/_android_work/NovaBAIC/app/src/main/java/com/verlintas/baic2/floatball/director/ProactiveCheckpoint.kt)
  同一调度面），新增「巡检班次」分支；频控按联系人分档（默认 1~4h 抖动），
  夜间静默复用 `DirectorRoutes.inQuietWindow`。
- **拉起 App 的合法性**：Android 10+ 后台启 Activity 受 BAL 限制，但本项目
  **常驻悬浮球 overlay（SAW）+ 前台服务**正属豁免路径（KeepAliveManager
  「先挂占位 overlay 再启」已有同款先例）；锁屏时跳过本轮（KeyguardManager 判断）。
- **巡检动作序列**（新组件 `ConversationListProbe`）：
  1. launcher intent 拉起 IM → 轮询前台包名 == imPackage；
  2. 会话列表页 `findText(联系人名)` 定位会话项；**微信优先走搜索直达**
     （点搜索框 → typeText 联系人名 → 结果列表点击），比长列表翻找可靠得多；
  3. 读会话项的未读角标（微信未读数是节点树里的文本节点「1」/「99+」，a11y 可读；
     需真机验证）→ 无未读 → back 退出收工；有未读 → 点进会话；
  4. 进入会话后接回合管线（读屏 → LLM → Gatekeeper → 拟人延迟 → SendSequence）。
- **成本与风控**：拉起-查看-退出动作拟人化（节奏随机化）；单轮巡检限 1 个 app；
  每日巡检次数上限；失败连续 N 次自动熔断暂停并通知用户。

### 8.4 S3 桌面角标：为什么不做

1. Android 无系统 API 读第三方 app 角标；角标由各 ROM launcher 私有绘制
   （多为自定义 View/badge drawable），**a11y 节点树大多读不到**（无 text）；
2. 即使可读也要求桌面恰在前台——后台托管场景下屏幕多半在别的 app；
3. 覆盖率与可靠性远低于 S2，投入产出不成比例。**弃**。

## 九、RPA 方案（docs/2026-10-15）必要性评估

### 9.1 结论：成立，且是「底座—应用」关系；但 A 期不必等它

对照自动聊天托管逐项核对 RPA 方案的四个坑与能力增量：

| RPA 项                                                              | 对自动聊天托管的直接影响                                                                                                                                    | 判定         |
| ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------ |
| **F3 节点上限 800 截断**                                            | 🔴 **直接命中**：`SendSequence.findSend` 同样走 `AndroidAccessibilityBridge.walk(800)`——微信长聊天窗+键盘弹起时「发送」按钮可能取不到 → 误报 SEND_NOT_FOUND | **必修**     |
| **F2 SET_TEXT 无粘贴兜底**                                          | 🔴 直接命中：微信输入框 SET_TEXT 可用，但淘宝/闲鱼自研输入框大概率拒绝 SET_TEXT——B 期电商客服的硬前置                                                       | **必修**     |

## 十、v2 无头全自动托管架构（对应反馈 (c)）

用户口径明确：**自动模式不弹分屏、不弹叠加窗，纯后台循环**：
监控 → 触发（通知/定时）→ 自动打开 App → 输入实际回复 → 驻留跟进一段时间 →
暂停 → 下一轮触发。LLM 分析全程后台。

### 10.1 形态定义

- **Headless 托管**为自动档的新运行形态，取代陪伴窗口的前台依赖：
  分屏面板（TranscriptView）**不挂载**，悬浮球保持常驻（它同时是 SAW 豁免的
  载体与用户手动介入的入口）；差分引擎照常由服务拉起，只是无 UI 观察——
  「通知后台回合」已证明不开分屏也能跑完整回合管线，无头化是同一形态的扩展。
- 截屏通道：跟进期用 **a11y `captureScreen()`**（API 30+，免授权、无系统弹窗、
  无投影指示灯；服务配置 `canTakeScreenshot` 已开），不再依赖 MediaProjection
  「拍完即关」。悬浮球在帧内的干扰由既有 OcrNoiseFilter/掩膜消化（连续参谋
  模式悬浮球常驻读屏已是既有先例）。

### 10.2 状态机与新组件

```
HeadlessAutoPilot 状态机：
  SUSPENDED(默认) ──S1通知/S2巡检──► NAVIGATING ──前台+SceneGate.CHAT──► CONVERSING
                                        │失败                              │
                                        ▼                                  ▼
                                    起草通知降级 ◄──发送失败── EXECUTING(注入/发送/确认)
                                                                           │成功
                                                                           ▼
                                                                     FOLLOWUP(驻留跟进)
                                       用户接管/超时/静默 ◄──(对方回复→下一回合)
                                       ▼
                                  SUSPENDED（等下一触发）
```

| 新组件                                        | 职责                                                                         |
| --------------------------------------------- | ---------------------------------------------------------------------------- |
| `HeadlessAutoPilot`                           | 总控状态机；三触发源接入；人在场检测（前台切走/用户触控即让路退出）          |
| `PatrolScheduler`                             | AlarmManager 巡检班次（§8.3），按托管联系人 app 集合轮转                     |
| `ConversationListProbe`                       | 会话列表未读检测 + 搜索直达（§8.3 序列）                                     |
| `ImNavigator`                                 | 双路径拉起：通知 contentIntent（S1）+ launcher intent（S2）                  |
| `FollowUpWatch`                               | 发送成功后的驻留监控（a11y 截图轮询对方回复；回复→回合；超时→back 退出挂起） |
| `SendableDraftExtractor` / `PostSendVerifier` | v1 方案不变（`<reply>` 标记协议 / 发送确认）                                 |

### 10.3 护栏升级（无人值守最高风险形态）

既有护栏全保留（默认关、白名单、拟人节奏、夜间静默、Gatekeeper 双审、指纹对账、
风险告知二次确认），新增：

1. **托管白名单独立且更保守**（≤3 人，与现有 autoWhitelist 分开）；
2. **每日自动发送总数上限**（新常量，触顶只出起草通知）；
3. **连续失败熔断**：连续 N 次 NAV/SEND 失败自动挂起托管并通知用户；
4. **人在场让路**：跟进期检测到用户切走前台/触控屏幕，立即 back 退出让路；
5. **托管总开关与陪伴窗口分开**（设置页新增「全自动托管」独立开关 + 独立风险告知文案）。

## 十四、巡检节奏 v3：自适应退避 + 会话驻留窗 + 链式闹钟

用户原始意图（2 次连续间隔 10 分钟、发现消息→自动监控 10 分钟→停止→循环）方向正确；
为同时满足**防杀、省电、防风控**三个目标，工程化为三件套（全部参数化）：

1. **自适应退避（防风控/省电核心）**：巡检间隔不是固定值，按「活跃度」分档动态调节——
   - 平静期（连续 K 轮未发现新消息）：间隔逐轮退避 `30min → 1h → 2h → 4h`（封顶，随机抖动 ±30%）；
   - 活跃期（本轮发现未读/刚完成会话）：下轮间隔收紧至 **10 分钟**（用户口径，参数可调），
     连续活跃上限 N 轮（默认 6 轮≈1 小时）后强制回退避曲线——**避免整天 10 分钟一次
     被平台风控盯上**；
   - 夜间静默（quiet 口径）完全停巡，静默结束不补巡（下一正常检点即可）。
2. **会话驻留窗（FollowUpWatch 时长语义）**：检测到新消息/发送成功后进入驻留监控
   （a11y 截图轮询为主、MediaProjection 录屏兜底——用户口径「无障碍模式+录屏兜底」采纳；
   a11y 通道异常（API<30 或截图连续失败）时才走投影授权）：
   - 对方持续回复 → 多回合循环（每回合 Gatekeeper→拟人延迟→发送）；
   - 驻留上限 10 分钟（参数可调）或连续 3 分钟无新消息即提前退出；
   - 退出动作：back 离开会话（回原界面）→ 挂起等下一触发。比固定 10 分钟更省电、
     更拟人（聊完即走）。
3. **链式闹钟（防杀/省电载体）**：不用长驻轮询，每轮检点完成即排下一次 one-shot
   `setExactAndAllowWhileIdle`（复用 M2-b 单班闹钟面，随机抖动）；进程被杀后由
   KeepAliveManager 既有三级降级复活 + 闹钟重排；锁屏期跳过拉起（KeyguardManager），
   只保留 S1 通知通道（通知监听不亮屏也能跑）。

参数表（全部进设置页，`AdvisorPrefs`）：

| 参数                   | 默认  | 说明                       |
| ---------------------- | ----- | -------------------------- |
| patrolBaseIntervalMs   | 30min | 平静期起始间隔             |
| patrolBackoffMaxMs     | 4h    | 退避封顶                   |
| patrolActiveIntervalMs | 10min | 活跃期间隔（用户口径）     |
| patrolActiveMaxRounds  | 6     | 活跃期连续轮数上限         |
| followUpWindowMs       | 10min | 会话驻留窗时长             |
| followUpIdleMs         | 3min  | 驻留内无新消息提前退出阈值 |
| dailySendCap           | 20    | 每日自动发送上限           |
| autoWhitelistMax       | 3     | 托管白名单上限             |

## 十七、R1 集成纪律四条（v4 用户指令）

### 17.1 a11y 执行面全面切换 assists 封装

用户事实判断成立：微信新版（首页/聊天/小程序/H5 混合页）节点文本稀疏且动态，
本方 `findText` 纯文本包含匹配 + `screenText` 扁平串，对最新微信的识别力不足；
assists 的结构化查询（按 resource-id/className/可点击父链的 `findById`/`findByTags`、
节点树 JSON、节点直接动作）才是能稳定解析微信对象树的通道。

落位：

- **保留 `AccessibilityBridge` 接口契约**（SendSequence/AgentLoop/tools 全部调用方零改动），
  **实现内部整体切换**：新建 app 层 `floatball/auto/AssistsA11yBridge.kt`，把
  `findText/screenText/tap/typeText/pressKey/...` 的实现委托给 `AssistsCore`
  （继承合体后全局实例可用）；`DeviceImplModule` 的 `@Binds` 换绑一行
  （与 F4 换绑合并为同一处 `[upstream-touch]`）；
- `TextNode` 语义保持（text+bounds），内部由 assists 节点树换源——上游调用方
  （tools/ui_control 等）自动受益于更强的微信解析力，无需各自改代码；
- 首选定位链升级为：**resource-id/描述精确匹配（assists 选择器）→ 文本包含匹配
  （现语义保留作兜底）→ OCR → 找图**（与 §6 RPA 找图链汇合）。

### 17.2 三模执行面（v5 修订：免 a11y 也要全自动托管）

用户明确需求：**无 a11y 时也要能全自动托管**。感知环无障碍成立（录屏抽帧+OCR+找图
能定位输入框/发送按钮坐标），缺的只是「坐标→点击」的注入通道。Android 平台注入
通道有且仅有三条：a11y 手势 / root / shell（adb-Shizuku）。据此执行面修订为三模：

| 模式                                | 感知面                              | 执行面                                           | 能跑什么                    |
| ----------------------------------- | ----------------------------------- | ------------------------------------------------ | --------------------------- |
| **A：a11y 模式**                    | a11y 树（assists）+ a11y 截图 + OCR | 节点动作/手势/SET_TEXT/粘贴                      | 参谋 + 全自动托管（现路线） |
| **B：Shizuku 模式（免 a11y 托管）** | **录屏抽帧 + OCR + 找图**           | **shell `input tap/text` 注入**（Shizuku shell） | 参谋 + **全自动托管**       |
| **C：纯感知模式**                   | 通知监听 + 录屏抽帧 + OCR + 找图    | 无（剪贴板代拟 + 跳转人肉粘贴）                  | 参谋 + 起草档               |

核心设计：**`InputInjector` 执行通道抽象**（floatball/auto，接口 + 双实现）：

- `A11yInjector`：现 SendSequence 底座（节点定位+手势/SET_TEXT）；
- `ShizukuInjector`：Shizuku shell 执行 `input tap x y` / 注入文本；SendSequence
  的「定位」改由录屏抽帧+OCR+找图产出的**坐标**驱动，「注入/点击」由 injector 执行——
  **定位与执行解耦后，三步状态机底座两种通道共用**；
- 选择逻辑：优先用户配置的通道；未配置时按可用性降级 A→B→C（C 不算「托管」，
  自动挂起草档）。

Shizuku 通道要点：

- **授权一次、长期免 a11y**：Android 11+ 「无线调试」可在手机端自启 Shizuku
  （无需电脑、无需 root）；本项目 device/impl 已有 Shizuku 依赖；
- **中文注入两条子路径**（shell `input text` 不支持 Unicode）：
  ① `cmd clipboard`（shell 权限可写剪贴板，13+）写入纯回复 → `input keyevent KEYCODE_PASTE`；
  ② 辅助 IME 广播注入（ADBKeyboard 同款机制，安装本方内置 IME，用户切一次输入法）。
  R1 验收时实测择优，默认 ①；
- **风控加分**：`input tap` 在系统输入层注入（InputReader 虚拟设备），目标 app
  侧无 a11y 服务可检测、无 a11y 节点查询痕迹——**比 a11y 模式更不易被微信识别**，
  正面回应「开无障碍可能被封杀」的顾虑；
- **检测面评估（2026-10-20）**：① 「USB/无线调试已开启」开关 app 可读但属弱信号
  （开发者模式普遍，「开着」≠「在被用」）；② Shizuku/adb **活跃会话对第三方 app
  不可知**（无公开 API/广播/日志）；③ 注入事件带虚拟设备 id 理论可查，主流 IM
  未见实际采用；④ 真正暴露面是行为模式（秒回/坐标机械重复）——拟人节奏、退避、
  上限护栏照常覆盖。结论：Shizuku 通道检测面比 a11y 小一个量级；
- **可用性代价**：无 root 时手机重启后 Shizuku server 需用户重新拉起（无线调试
  一键自启，不需电脑）——托管/巡检遇 Shizuku 断连自动降级 C 档起草并通知用户；
  root 用户可开机自启消除该成本；
- 免 a11y 模式下的巡检/导航同样成立：launcher 拉起是普通 startActivity；会话
  列表未读检测由「录屏抽帧+OCR/找图」替代 a11y 树（更慢但可跑）；锁屏跳过逻辑不变；
- 代价（设置页明示）：录屏授权弹窗 + 状态栏指示灯（可先静默感知后集中执行窗口），
  找图定位比 a11y 树慢（ROI 优先缓解）。

### 17.3 帧源阶梯（OpenCV 与 OCR 的输入统一）

RPA 文档原设计「只用 a11y 截图」按用户指令修订为**帧源接口双通道**：

```
FrameSource 阶梯：a11y captureScreen（API30+，免授权，首选）
                 → MediaProjection 抽帧（免 a11y 模式 / a11y 截图连续失败时兜底）
                 → ImageMatcher(image) / OcrProvider(image)
```

- `ImageMatcher` 只认 `FrameSource` 产出的 Bitmap，不关心来源——同一套找图
  逻辑在两种模式下复用；
- 免 a11y 模式的录屏帧源 **采用 assists-mp**（2026-10-20 用户决策：mp 带入、
  不动 assists 代码）——它是 assists-opcv 的原生配套帧源，opcv→mp 链路闭合
  零裁剪；自家 `FloatCaptureBridge` 保留于屏幕参谋投影读屏（既有链路不动），
  两套投影各守领地：**参谋=自家链，自动托管找图=assists-mp**；
- assists-mp 的授权中转（MediaProjection 必须由 Activity 发起，铁律 §8.2）与
  Android 14+ 一授权一投影的兼容性在 R1 第 5 步实测；抽帧节流复用
  FrameDiffEngine 节奏参数（省电）；
- 录屏兜底的代价（授权弹窗、状态栏指示灯、Android 14+ 一授权一投影）在
  设置页文案与风险告知中明示。

## 二十三、A 期入口向导与托管对象选择（v7，2026-10-20 用户指令）

### 23.1 交互流程（三步向导，作为托管唯一开启入口）

单击「自动」子球 → 弹向导面板（overlay，视觉风格同分屏浮窗/设置卡片）：

1. **第①步 选 App**：列出感知白名单内 IM（微信 / 企业微信 / QQ / TIM / 钉钉 /
   飞书 / Telegram），勾选要托管的 App；**淘宝 / 闲鱼 / 拼多多灰显占位**
   （B 期电商客服，角标注明「B 期开放」），不消失——向用户明示路线图。
2. **第②步 选联系人**：按所选 App 过滤已建档联系人，勾选托管白名单（上限沿用
   `autoWhitelistMax`）；**未勾任何联系人 = 该 App 仅感知 + 起草，不自动发**
   （起草档语义，护栏不降级——选了微信不等于微信里所有人都能被代发）。
3. **第③步 就绪检测**：`ReadinessGate` 八项探针（§20.1）当场重跑，全绿 →
   开启托管（悬浮球进 AUTOPILOT 第四态，§十五）；有缺项 → 红行明细 +
   修复入口，保持向导不关闭。风险告知二次确认从设置页移入本步全绿后弹出。

上次选择回显（`AdvisorPrefs`），再次进入默认勾选、可一键沿用。

### 23.2 语义与数据

| 层                             | 数据                                      | 作用                                                          |
| ------------------------------ | ----------------------------------------- | ------------------------------------------------------------- |
| App 集合（新增）               | `AdvisorPrefs.autopilotApps: Set<String>` | S2 巡检轮转范围（§8.3）+ 通知解析放行范围                     |

| 组合语义                       | —                                         | 勾 App 未勾人 = 感知+起草；勾 App 且联系人绑定该 App = 全自动 |
