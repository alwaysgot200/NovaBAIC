# 接管与达成通报（Escalation）方案（2026-10-20）

> 回答两个问题：①「对方问出 LLM 答不了又避不掉的问题 / 目标达成」这类**实务响应型**聊天内容如何判定；②判定职能分给哪个子代理。
> 落位：全部新增于 `floatball/` 包，零上游侵入，零 Room 迁移。

---

## 一、结论先行

两类场景，两个判定出口，一个执行面，**不新增第六个常驻 LLM 代理**：

| 场景 | 代号 | 判定归属 | 依据 |
| --- | --- | --- | --- |
| 对方提出只有用户本人才能回答的问题（几点回家/发照片/来不来吃饭） | **H（Handoff 接管型）** | **Director 路由层**：新增 `HANDOFF` 路由；判定器 = 确定性词表（`HandoffRules` 纯函数）+ 轻 LLM 兜底（`HandoffGate`） | 这判的是**对方来信的属性**，发生在 Responder 生成**之前**——判成接管就不该让 LLM 硬答，属于「本轮该干什么」的路由职能（方案 §2.3：LLM 只在发什么环节介入，不在做什么环节兜圈子） |
| 对方表态推进/达成目标（同意见面、同意购买、约好时间地点） | **G（GoalHit 达成型）** | **MissionJudge 既有裁决职能**（`advanced`/`branch`/`l1Completions` 产出点已存在）+ 新增确定性快通道（`GoalHitRules`） | 达成判定是回合结局裁决，Judge 已在做且有 evidence 约束；缺的只是「通知主人」的出口旁路 |

执行面：新增 `EscalationNotifier`（`floatball/notify/`）——**铃声通知（必发）+ SMTP 邮件（新通道）+ 台账回放 + 自动发送挂起**。

与 Gatekeeper 的关系：Gatekeeper 的 `AUTO_REGEXES` 审**我们发出去的稿**（拦报价/承诺/隐私/超阶段），H 词表审**对方进来的话**（识别索取/日程/决策）——方向相反、同族同构，词表纪律一致（**宁严勿松**：漏报=无人值守编造事实，代价远大于误报多打扰一次）。

## 二、H（接管型）判定设计（v2 修订：LLM 主判定）

### 2.1 判什么

判的不是「LLM 答不了」——LLM 什么都能编。判的是**「正确答案只有用户本人持有」**：答案依赖用户的真实日程、真实资产（照片/文件）、真实事实（住址/家庭/偏好）、真实决策（去不去/选哪个）。LLM 代答 = 编造 = 事故。

### 2.2 判定权重反转（v2，用户拍板）

用户对纯规则字符匹配的**漏判/错判**风险的担心成立——中文表达太灵活（「到家了吗」「来一个呗」「那个东西传我一下」「把位置甩我一下」词表穷举不完）。v2 把判定权重反转：

```
来信文本（IncomingCue.latestIncoming 已抽取）
   │
   ├─ 快筛白名单（HandoffRules.whitelistHit，极保守）：
   │    纯表情/纯肯定（好·行·嗯·OK）/超短欢呼 → normal，跳过 LLM（省成本）
   │
   ├─ 主判定：HandoffGate 轻 LLM 分类 —— 自动域内每条来信必跑
   │    ≤120 tok / 8s 超时 / few-shot 例句库（assets/handoff_examples.json，
   │    四类×每类 8+ 条多样表达，枚举库「大」落在例句里让 LLM 泛化）
   │    → {"kind":"handoff","category":"实体索取|日程出席|私人事实|决策请求"}
   │      {"kind":"normal"}
   │
   ├─ 高置信词表直判（HandoffRules.strongHit，宁严勿松）：
   │    强模式命中（如 几点.{0,4}(回|到)家 / (照片|定位|地址|验证码).{0,8}发(给)?我）
   │    → 直接 HANDOFF，不等 LLM（也作为 LLM 判 normal 时的否决票，见下）
   │
   └─ 降级备胎：LLM 超时/无配置/畸形输出 → 词表兜底判定
```

**合并逻辑（OR，宁严勿松）**：`strongHit || llm==handoff → HANDOFF`；LLM 判 normal 但 strongHit 命中仍以词表为准（误接管代价 = 主人多看一眼通知；漏判代价 = 无人值守编造事实，不对称）。

**成本**：自动域内每条来信 ≤120 tok 分类，相对回合本身（T1 取数+Responder 数百 tok）增量 <10%，且 PromptDedup 已挡掉 OCR 抖动重复来信，不会重复计费。

**失败降级链**：LLM 故障 → 词表 strongHit 兜底 → 仍不确定则 normal + 生成端「不编造」约束兜底（绝不因分类器故障打断回答链）。

### 2.3 四类判据（词表与例句库共用此分类）

| 类别 | 典型来信 |
| --- | --- |
| 实体索取 | 「把上次的照片发给我」「发个定位」「把那个文件传我一下」 |
| 日程出席 | 「你今天几点回家？」「晚上去xxx吃饭你来么？」「什么时候到家」 |
| 私人事实 | 「你家住哪」「你工资多少」（与 Gatekeeper.AUTO_PRIVACY 词表复用，方向反转） |
| 决策请求 | 「A 还是 B？」「能不能答应他」「要不要接这个单」 |

### 2.4 uncertain 处置（v2 已拍板：默认宽松）

uncertain → 放行正常回答，但生成端系统提示词追加约束「不编造个人事实（日程/住址/家庭/资产），遇不确定的私人问题用含糊回避话术留待用户」（与 `autoForbiddenSection()` 同一追加机制）。严格档（uncertain → 降级起草）保留为设置开关，默认关。

### 2.5 H 命中后的行为（关键联动）

1. **本回合不自动发送**：自动档（CompanionWindow）跳过 Responder 自动发送；通知链后台回合只出通报不出草稿（通报本身就是草稿入口）。
2. **该联系人自动发送挂起**（await-human 内存态）：直到用户在分屏对该联系人发出一条消息才解除。防止 LLM 绕过用户继续自动回复「我晚上八点到家」。
3. **发通报**：铃声通知 + 邮件（§四）。
4. **台账**：director_logs 落 `route=handoff, reason=incoming_handoff`，turnMessageId 三层回放链照常闭合。

## 三、G（达成型）判定设计

### 3.1 快通道（当回合生效，新增）

`GoalHitRules.hit(incoming)` 确定性词表：对方**明示同意/敲定**——「好呀」「行，那就明天见」「可以，价格没问题」「成交」「那就这么定了」「发我地址吧」。命中 → 当回合立即通报，不等下一回合 Judge。

误报面控制：只收「同意/敲定」类肯定表态，不猜「考虑一下/再看看」（那是进行中，不是达成）。

### 3.2 慢通道（Judge 裁决出口旁路，复用既有产出点）

`MissionJudgeRunner.JudgeOutcome` 已有三个达成信号（MissionJudgeRunner.kt L109-113）：

- `missionResult=advanced` 且 advanceSignals 规则同向命中；
- `branch != null`（阶段跃迁提议）；
- `l1Completions` 高置信（confidence≥0.8）。

在 `JudgeOutcome` 消费点（ScreenAdvisor T1 strategyDeferred 内，现为 UI 态更新）**追加** EscalationNotifier 旁路调用，附 evidence 行。零重复实现——达成裁决的逻辑（有向图/信号词/置信门）一行不动。

### 3.3 去重

- 快通道：同人 30 分钟节流（与 H 共用查询，§四.4）。
- 慢通道：同联系人同阶段只通报一次（查 director_logs 最近 `reason=goal_hit_*` 行的阶段码比对）。

## 四、通知执行面（EscalationNotifier，`floatball/notify/`）

### 4.1 本地铃声通知（必发、必达底线）

- 新渠道 `floatball_escalation`：`IMPORTANCE_HIGH` + 声音 + 震动 + `CATEGORY_ALARM`；Manifest 追加 `USE_FULL_SCREEN_INTENT`（锁屏弹全屏横幅，正常权限免申请流程）。
- 通知 id：`2_100_000 + contactId` 派生，与起草通道 `2_000_000` 不撞。
- 点击 → 复用 `ACTION_SHOW_DRAFT` 路径拉起分屏（带触发原因与来信摘录），用户当场接管回答。
- 权限：走 `NotifyGate`（POST_NOTIFICATIONS 已由现有链管理）。

### 4.2 邮件通道（E3 期，新依赖）

- **SMTP 直发**（本地优先合规：App 保持纯 HTTP/出站客户端角色，无端口监听、无服务端，不触红线）。
- 依赖：`com.sun.mail:android-mail:1.6.7` + `android-activation`（libs.versions.toml 加两行，APK 增量 ≈2MB）。
- 设置页（FloatSettings）新增 SMTP 配置：预设 QQ 邮箱（smtp.qq.com:465）/ 163 / Outlook / 自定义；**授权码**输入（非登录密码，各邮箱开 SMTP 即得）。
- 邮件内容模板：联系人名 + 所属 IM + 触发类型（接管/达成）+ 来信原文摘录 + 证据行 + 时间。**即取即用不落盘**（本地优先红线，同 M2 通知纪律）。
- 失败静默降级（本地通知必达是底线），失败计数进周报对账（DirectorLedgerStats 口径）。

### 4.3 备选通道：Webhook（极低成本，建议并入 E3）

通用 `POST 用户配置 URL`——Server酱/PushPlus（→微信服务号推送）/Bark（iOS）都是现成免费出口。App 已是 HTTP 客户端，加一个通道实现 ≈50 行。是否要，待拍板（§十.3）。

### 4.4 频控与时段纪律

| 项 | 规则 |
| --- | --- |
| H 节流 | 同联系人 30 分钟内不重复（查 director_logs 最近 handoff 行时间戳） |
| G 节流 | 同联系人同阶段 1 次 |
| 静默时段 | **H 不受 quiet window 约束**（紧急性质，深夜来的「几点回家」更要通报）；**G 遵守静默时段**（成交消息不急于深夜吵醒，早上看邮件即可）——待拍板（§十.4） |

### 4.5 生效域（不通知「在场的自己」）

| 模式 | 行为 |
| --- | --- |
| 单次/连续参谋（人已在分屏前） | 不发铃声/邮件；分屏内出提示条（免打扰级别） |
| 自动档（CompanionWindow）+ 托管通知链 | 铃声 + 邮件全量 + 自动发送挂起（仅 H） |

## 五、归代理结论（回答「分给哪个子代理」）

| 职能 | 归属 | 为什么不是新代理 |
| --- | --- | --- |
| 接管判定 | **Director**（路由表 + `HANDOFF` 路由）+ `HandoffRules`/`HandoffGate` 两个判定器 | Director 的职责就是「本轮该干什么」；HANDOFF = 本轮不代答转人，是路由决策不是生成任务。判定器是纯函数+一次轻分类，养不起也不需要常驻代理 |
| 达成判定 | **MissionJudge**（既有裁决出口加旁路）+ `GoalHitRules` 快通道 | Judge 已在裁决 advanced/branch/l1Completions，机制、evidence、置信门全是现成的 |
| 通报执行 | **EscalationNotifier**（执行面新组件，非决策面） | 与 ActionDispatcher/Gatekeeper 同层：纯执行，不做判断 |

系统提示词级约束同步追加（生成端第一道防线）：自动档 forbidden 追加「不编造个人事实（日程/住址/家庭/资产），遇不确定的私人问题以含糊话术回避并留待用户」。

## 六、数据与台账（零迁移）

- `DirectorRoute` 枚举加 `HANDOFF`；`AdvisorEntities.kt` 加 `ROUTE_HANDOFF = "handoff"`（route 列是 TEXT，新值零迁移）。
- `DirectorInput` 加 `isHandoff: Boolean = false`（调用方判定后传入，路由表保持纯函数）；`decide()` INCOMING 分支：`if (isHandoff) HANDOFF to "incoming_handoff" else REPLY to "incoming_default"`。
- reason 码：`incoming_handoff` / `goal_hit_fast` / `goal_hit_judge` / `escalation_throttled` / `await_human`。
- 回放链：turnMessageId 锚点照常，`DirectorLedgerStats` 周报追加 H/G 命中数对账。

## 九、风险与权衡

1. **词表覆盖 vs 误报**：中文表达多样，词表必有漏。防线是三层：词表 → 轻分类 → 生成端「不编造」约束。即使 H 漏报，Responder 被禁止编造私人事实，最坏输出是回避话术而非事故答案。
2. **SMTP 凭据**：v1 存 AdvisorPrefs（SharedPreferences）。敏感度低于 API Key（授权码可随时吊销重开），但保留升级 Keystore 的口子——待拍板（§十.2）。
3. **依赖体积**：JavaMail ≈2MB，release 双 ABI 收敛后实际增量更小，远低于 assists 集成的 22~30MB 基线。
4. **通知风暴**：节流 + await-human 挂起保证同联系人不会连环轰炸；多联系人并发各走各的派生 id，互不覆盖。
5. **与 M2 起草链的边界**：起草档每封信本来就通知人（人已在环），H 通报只服务自动档/托管——不叠加双通知。

## 十、决策记录（2026-10-20 用户拍板）

1. **uncertain 默认档**：✅ **宽松**（放行+生成端回避约束）；严格档保留为设置开关默认关。
2. **SMTP**：✅ 设置页可配 SMTP server；**测试环境默认配置内置**（阿里企业邮箱）：
   `smtp.qiye.aliyun.com:465` / SSL / `marketing@80fafa.com` / 发件人名「80lili帮您理理」/ 超时 30s。授权码为测试凭据，正式发布前由用户在设置页改写；v1 存 AdvisorPrefs。
3. **Webhook 通道**：✅ 本期**不做**；未来可能改为「系统直接发微信消息给某人」，通道抽象预留接口不实现。
4. **时段纪律**：✅ G 遵守 quiet window 深夜静默；H 全时段通报。
5. **H 判定架构**：✅ 用户担心纯规则词表漏判/错判 → v2 权重反转为 **LLM 主判定（每条来信必跑）+ 大例句库 few-shot**，词表降级为快筛白名单 + 强模式直判 + 故障降级备胎（§2.2）。
