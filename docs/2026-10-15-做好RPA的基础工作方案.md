## 1. 背景与目标

上游 NovaBAIC 已内置一套"无障碍树优先、OCR 兜底、LLM 编排"的 RPA 底座（`open_app`、
`ui_control`、ACT/MAX 模式、逐动作确认闸门），但距离"健壮可靠稳定高效"还差三类基础：

1. **识别面不全**：只有节点文本与 OCR，没有"以图找图"，对无文本图标、Flutter/H5
   稀疏节点界面（闲鱼等）能力不足；
2. **现有执行链路有 4 个已查实的坑**（见 §5），会直接导致误报失败、输入失败、
   节点截断、OCR 兜底失效；
3. **底层封装不够厚**：选择器、手势、步骤器等需要沉淀，避免后续每个 RPA 场景都手搓。

本方案只做**基础工作**，不做具体业务自动化（不写微信/闲鱼话术机器人）。目标：

- 引入成熟开源框架 **assists**（`assists-base` + `assists-opcv`），获得官方
  OpenCV Android SDK 与增强无障碍封装；
- 修复 4 个现实坑；
- 建成一条性能预算明确（节点操作 10–50ms、全屏找图 ≤100ms、ROI 找图 ≤20ms）、
  有成功校验、有降级路径的 RPA 基础通道。

### 3.2 API 形态（评估后确认可直接用）

- **`AssistsCore`**（约 96KB 的门面单例）：`init(Application)`、服务开关检测与跳转、
  `getAccessibilityRootNodes(scope)`、`findById(...)` 选择器、节点点击/输入/滚动、
  手势派发、截图、剪贴板等；
- **`AssistsService`**：`open class AccessibilityService`，持有全局实例引用、
  分发连接/事件/解绑监听器。**可被我方服务直接继承**；
- **`OpencvWrapper`**（`assists-opcv`）：
  - `matchTemplate(image, template, mask)`（固定 `TM_CCORR_NORMED`）；
  - `matchTemplateFromScreenToMinMaxLoc()`：native `Core.minMaxLoc` 取最佳点，**快**；
  - `getResultWithThreshold()`：多目标阈值提取；
  - `createMask()`：HSV 掩膜；
  - `getTemplateFromAssets()`：assets 模板装载；
  - `getScreenMat()`：内部走 `MPManager`（assists-mp 的 MediaProjection）。
- **AAR 清单合并带入**：`READ/WRITE_CONTACTS` 权限、`${applicationId}.assists.fileprovider`
  FileProvider、透明 `ClipboardActivity`。

### 3.3 已识别的框架短板（集成时必须绕开，不能盲信）

1. **`getResultWithThreshold()` 性能陷阱**：它用 Kotlin 双层循环逐像素取
   `result[y,x]`（每次分配 `double[]`），全屏结果矩阵上百万点，实测会退化到
   数百毫秒至秒级。多目标场景我方改用 native `Imgproc.threshold + Core.findNonZero`
   + NMS，单目标直接用 `minMaxLoc`。
2. **`TM_CCORR_NORMED` 对亮度/底色变化敏感**：深色模式、状态栏遮罩会造成误匹配。
   我方封装默认改用 **`TM_CCOEFF_NORMED`**（去均值，亮度不敏感），并保留方法可选。
3. **截图不要用 `OpencvWrapper.getScreenMat()`**：它绑定 assists-mp 的投影授权。
   我方一律用自有 `AccessibilityBridge.captureScreen()`（API30+ 免授权、无弹窗、
   无指示灯）取帧后自行 `Utils.bitmapToMat`，与老参谋感知阶梯保持同一通道。
4. **不启用第二套执行栈**：assists 传递依赖 utilcodex、MMKV、OkHttp、Gson。
   动作执行仍以我方 `AccessibilityBridge`（已打通 DI/老参谋/闸门）为主通道，
   assists 能力以"补充增强"方式经独立门面调用，不双轨并行。

## 4. 接入方式与分支策略（含 3 个待决策项）

### 4.1 决策 D1：submodule 如何使用——"源码参考 + Maven 构建"（推荐） vs "源码 include 构建"

用户提议添加子模块并使用其中的 `assists`、`assists-opcv`。子模块照加，但**是否纳入
Gradle 构建**需要在评审时拍板：

| 维度 | 方案甲：submodule + `include()` 源码构建 | 方案乙（推荐）：submodule 仅作源码/许可/调试锚点，构建走 Maven Central AAR |
| --- | --- | --- |
| `settings.gradle.kts` | 需追加 include（白名单外文件，上游合并新增冲突点） | **零改动** |
| 子模块构建脚本 | 其模块 `build.gradle` 依赖 `rootProject.ext.compileSdk/minSdk/opencvVersion…`、`apply plugin 'com.vanniktech.maven.publish'`、`apply from rootProject.file('gradle/publish-maven-central.gradle')`，在我方根工程下**直接构建必失败**，须持续维护 fork 补丁 | 不执行其构建脚本，无此问题 |
| 仓库模式冲突 | 我方 `FAIL_ON_PROJECT_REPOS` 与其 `allprojects{repositories}` 冲突 | 无 |
| 构建性能 | 多模块 + kapt（assists 用 kapt）拖慢全量构建 | 只消费 AAR |
| 升级方式 | 手动 rebase 补丁 | 版本目录改一个号 |
| 可改源码/断点 | ✅ | 可在 submodule 副本里改后本地验证，修复**提 PR 给上游**；正式构建仍用 AAR |
| 产物一致性 | 自己编译 | 与官方 Demo、生态文档完全一致 |

**推荐方案乙**：

```bash
git checkout laocanmou
git checkout -b lcm
git submodule add https://github.com/alwaysgot200/assists.git thirdparty/assists
git -C thirdparty/assists checkout 5f5e3bb769fae24ff403434368e2b977be5f78af
```

- `thirdparty/assists/` 不进 `settings.gradle.kts`；根 `.gitignore` 无需条目
  （submodule 本身受控，其内部构建产物在子仓 .gitignore 内）；
- 依赖走版本目录（§4.3），版本固定 **3.5.9**（实施时先查 Maven Central 是否有更新
  稳定版，更新需在任务记录中注明）；
- 评审若坚持方案甲，需额外承担上表全部改造成本，本文不推荐。

### 4.2 决策 D2：无障碍服务如何与 assists 合体（推荐一行级继承）

`AssistsCore` 依赖 `AssistsService.getOrNull()` 全局实例。两个选项：

- **方案甲（推荐，2 处一行级 `[upstream-touch]`）**：让现有
  `Baic2AccessibilityService` 改为继承 `AssistsService`（而非直接继承
  `AccessibilityService`）。Manifest 组件名、服务配置 xml、`bridge.attach()`
  全部不变（子类仍是一个 `AccessibilityService`）；`AssistsService.onCreate/
  onServiceConnected` 经 `super` 调用自动完成注册。
  - `device/impl/build.gradle.kts`：增加 `api(libs.assists.base)` 一行；
  - `Baic2AccessibilityService.kt`：父类替换一行，补 KDoc 注明来源；
  - 无障碍设置里**始终只有一个开关**，用户体验与现状完全一致。
- 方案乙（零触碰备选）：app 模块新建第二个服务并在 app manifest 用
  `tools:node="remove"` 移除库服务声明后重新接线，同时改造 bridge 的 attach 类型。
  代码量大、两套服务生命周期，不推荐，仅在评审否决一切上游触碰时启用。

### 4.3 工程接线清单

1. `gradle/libs.versions.toml` 新增：
   `assists = "3.5.9"`、`assists-base`、`assists-opcv` 两个库坐标；
2. `device/impl/build.gradle.kts`：`api(libs.assists.base)`（D2 方案甲需要）；
   `app/build.gradle.kts`：`implementation(libs.assists.opcv)`（OpenCV 只进 app，
   不污染其他模块）；
3. **ABI 与体积**：OpenCV AAR 含 4 ABI 原生库，全量会使 APK 增大约 35–50MB。
   debug 需保留 `x86_64`（模拟器 Galaxy_Intel_API_36），release 收敛：
   `ndk { abiFilters += listOf("arm64-v8a", "armeabi-v7a", "x86_64") }`，
   真机主流是 arm64（单 ABI 增量约 15–20MB）；
4. **清单合并治理**（`app/src/main/AndroidManifest.xml` 追加，白名单文件）：
   用 `tools:node="remove"` 移除本项目不用的 `READ_CONTACTS/WRITE_CONTACTS`；
   复核 FileProvider authorities 不与现有 provider 冲突；
5. **初始化**：`Baic2Application.onCreate()` 追加（app 模块常规改动）：
   `AssistsCore.init(this)` 与 `OpencvWrapper.init()`（后者内部已异步加载本地库，
   首次找图前预热）；
6. **依赖冲突排查**：assists 传递 OkHttp 4.10、Gson、utilcodex、MMKV。
   实施后先跑一次 `:app:dependencies`，若与项目现有 OkHttp 版本冲突则在
   app 依赖处统一排版本；不新增直接 new OkHttp/Gson 的自研代码，红线不变；
7. 新增代码全部在 `app/src/main/java/com/verlintas/baic2/rpa/`，
   新文件带 GPL-3.0-or-later 头，用户可见文案进 `strings.xml`（`rpa_*` 键）。

## 5. 四个现实坑的修复设计

> F1/F2/F4 直接改上游文件（lcm 分支最小 diff + `[upstream-touch]`）。
> 已验证：F1/F4 存在"app 侧 dynamic 同名覆盖"的零触碰备选路径（见各节备注），
> 但在专属 lcm 分支上推荐源头修复，diff 可读、不复制整份工具代码。

### F1（最高优先）· 点击成功被误报失败，可能诱发重复发送

- **现状**：`UiControlTool.pointerAction` 点击后取 `screenSignature()`，
  其实现只有 `包名 / 窗口标题`（`tools/UiTools.kt` 第 342–346 行）。微信聊天页
  发消息前后两者都不变，永远返回 `Screen unchanged`，模型可能判定未发送而重发。
- **修复**（`tools/UiTools.kt`，纯函数易测）：
  1. 新签名 `ScreenSignature(pkg, title, nodeCount, textFingerprint)`，
     `textFingerprint` = 对 `accessibility.screenText(200)` 归一化（trim、去空白行）
     后的稳定哈希；新气泡出现即变；
  2. `tap` 增加可选 `expect` 参数：提供文本时走 `wait_for` 同款轮询
     （复用现有 400ms 节拍、上限 3s），出现预期文本即明确成功；
  3. 签名未变时**不再输出带失败暗示的文案**，改为中性结果：
     "已点击 (x,y)，屏幕结构未观测到变化（部分操作本就无界面变化，如发送/勾选，
     勿重复同一动作）"，并提示可用 `find`/`expect` 复核；
  4. 配套熔断：同一坐标连续两次点击且签名不变，第二次结果附 `possibly_duplicate`
     标记，供 ACT 确认弹窗强提示"该操作可能已执行过"。
- **验收**：微信聊天窗发送消息返回成功/中性，不再出现诱导重发的 `unchanged`；
  开关类控件（无文本变化）不报失败；`expect` 命中路径有单测。
- 零触碰备选：app 侧实现 `RobustUiControlTool` 并 `registerDynamic` 同名覆盖
  （`byName + dynamic` 同名以后者胜），不动 `tools` 模块。

### F2 · SET_TEXT 全量替换且被自研输入框拒绝，缺粘贴兜底

- **现状**：`AndroidAccessibilityBridge.typeText()` 只做 `ACTION_SET_TEXT`
  （整体覆盖），失败仅返回 `set_text_rejected`，没有兜底。
- **修复**（`device/impl/.../AndroidAccessibilityBridge.kt`，三级降级）：
  1. `ACTION_SET_TEXT`（空输入框、标准控件，10–30ms，保持现状优先）；
  2. 失败 → 保存当前剪贴板文本 → `ClipboardManager` 写入目标文本 →
     节点 `ACTION_PASTE`（不经 IME，中文直达，兼容多数自研输入框）→
     延迟一拍恢复原剪贴板内容；恢复失败不阻断结果但记录日志；
  3. 仍失败 → 保留现有明确 reason，新增 `clipboard_paste_rejected`，
     由上层映射用户文案。
- 语义补充（`tools/UiTools.kt` type 动作）：新增 `mode` 参数，
  `replace`（默认，同现状）/`append`（读聚焦节点现有文本拼接后 SET_TEXT，
  解决"全量替换"在非空框的问题）。
- **验收**：标准框走第 1 级；模拟拒绝 SET_TEXT 的框走第 2 级成功且剪贴板复原；
  微信输入框 append 不清空已有文字。
- 备注：剪贴板动作属 HIGH 敏感情形，ACT 模式下该工具调用仍走逐次确认闸门，
  不新增无人值守例外。

### F3 · 节点上限 800 可能截断微信长聊天窗

- **现状**：`AndroidAccessibilityBridge` 遍历常量 `MAX_NODES = 800`
  （第 261–263 行），`findText/screenText` 共用，键盘弹起 + 长消息列表时尾部
  元素（含底部"发送"按钮）可能取不到。
- **修复**：常量上调至 **4000**；`walk` 增加可配置上限参数，`findText/screenText`
  透传调用方的 `maxNodes`（screenText 现已有参数，findText 补同名参数，默认 4000）；
  遍历保持现有每节点 `runCatching`，不新增长生命周期对象引用。
- **验收**：微信长聊天窗 + 键盘弹起状态下 `find "发送"` 稳定命中；
  4000 节点遍历在模拟器实测 <50ms（超阈值则下调为 2500 并在文档记录）。

### F4 · OCR 兜底错走 MediaProjection，未授投影时直接失败

- **现状**：`ToolContext.screenshot` 由 Hilt 绑定到
  `AndroidScreenshotProvider`（投影）；`ui_control` 的 find/tap OCR 兜底、
  `screen_ocr` 都调它。无障碍免授权截图 API（`captureScreen()`，API30+）
  已实现却只被老参谋感知层使用。
- **修复**（推荐 1 新增 + 1 行 `[upstream-touch]`）：
  1. `device/impl` 新增 `PreferA11yScreenshotProvider`：实现
     `ScreenshotProvider`，`capture()` 内部阶梯 = 无障碍 `captureScreen()`
     （API30+，免授权）→ 失败/低版本再委托现有投影实现；`ready`、权限 intent、
     `release()` 全部委托投影实现，投影"拍完即关"策略不变；
  2. `DeviceImplModule.kt` 的 `@Binds` 换绑到新实现（一行）；
  3. 回归确认：老参谋 `ScreenPerceiver` 现有四级阶梯行为不回退
     （它先自调 a11y，再调 provider；新 provider 只是多一次快速失败尝试，
     必要时让其直接持有投影实现的限定注入，实施时二选一，以冒烟结果为准）。
- **验收**：不授投影时主 App `ui_control find` 的 OCR 兜底可用；
  API29 及以下自动落到投影授权流程；老参谋冒烟链路全部通过。
- 零触碰备选：F1 的 `RobustUiControlTool` 直接注入 `AccessibilityBridge`
  自行做截图阶梯，完全绕开 `ToolContext.screenshot`。

## 6. "以图找图"能力设计（app 模块 `rpa.cv` 包，新增不侵入）

### 6.1 定位与链路

```
模板资产(assets) ─┐
                 ├─► ImageMatcher（纯计算，Dispatchers.Default）
屏幕帧(a11y截图) ─┘        │
                           ├─ 单目标: matchTemplate + minMaxLoc（全 native）
                           ├─ 多目标: matchTemplate + threshold + findNonZero + NMS
                           └─ 输出: Match(centerX, centerY, score, rect, method)
                                        │
                          RpaImageTool（find/wait/tap，注册进 ToolRegistry）
                                        │
                          点击后走 F1 的签名/expect 校验，闭环
```

- **帧来源**：只走 `AccessibilityBridge.captureScreen()`，不使用
  `OpencvWrapper.getScreenMat()`（避免投影授权与指示灯）；
- **计算源**：OpenCV 4.9.0（经 `assists-opcv` 引入的官方 AAR）。
  `OpencvWrapper` 的 `matchTemplate` 与资产装载可复用；阈值提取与截图路径
  按 §3.3 用我方实现，不踩性能陷阱。

### 6.2 健壮性设计（"可靠"的具体含义）

1. **方法默认 `TM_CCOEFF_NORMED`**：去均值，深色模式/亮度变化不敏感；
   保留 `TM_SQDIFF_NORMED`/CCORR 作为按场景配置项；
2. **alpha 掩膜**：模板 PNG 透明区域自动转 mask，不规则图标（圆角按钮）
   不带入背景像素；同时支持 assists 的 HSV `createMask` 处理固定色彩图标；
3. **多尺度**：以 720p 为基准制作模板，运行时按屏宽比缩放（0.9/1.0/1.1 三档），
   取最高分；高 DPI 设备不失效；
4. **灰度优先开关**：色彩无关图标走灰度匹配，进一步降耗时、抗主题差异；
5. **ROI 优先**：调用方可传区域（如"底部操作条"），命中即停；全屏失败后
   按预设热点区域（顶部栏/底部栏/右侧）二次尝试，而非全屏重算；
6. **阈值治理**：默认 0.80（CCOEFF），结果返回原始分数；低于阈值不点击，
   返回最佳分数与坐标供模型判断；禁止"差一点也硬点"；
7. **模板版本与机型台账**：模板文件名编码基准宽度与适用 App 版本
   （`wechat/send_btn-w720.png`），App 改版导致失配时可按台账更新，
   不把阈值调成"碰运气"；
8. **不做的事**：不联网传图、不把屏幕帧落盘（本地优先红线）；
   模板制作中间截图只放 `tests/tempImg/`，成品 PNG 才入 assets。

### 6.3 性能预算（真机/模拟器实测门禁）

| 操作 | 预算 | 说明 |
| --- | --- | --- |
| 帧获取（a11y 截图 → Bitmap） | ≤120ms | API30+ 同进程 |
| 全屏模板匹配 720p（100×100 模板） | ≤60ms | native，arm64；首次含库预热另计 |
| ROI（300×120）匹配 | ≤20ms | |
| 多目标提取（native 路径） | ≤30ms | 禁用 assists 的 Kotlin 逐像素实现 |
| find → tap 端到端 | ≤300ms | 含点击手势 60ms |

不达标项不得合并；在模拟器（x86_64）与 arm64 真机各出一组数据记入验收。

### 6.4 暴露给模型的工具协议（dynamic 注册，不动内置工具表）

- `image_find`：参数 `template`（资产名）、`threshold?`、`region?`、
  `scale?`、`multi?`、`method?`；返回全部命中点（坐标+分数+区域）；
- `image_wait`：模板出现/消失轮询（复用无障碍事件优先、超时默认 6s）；
- `image_tap`：find + tap 一步完成，**内置 F1 同款变化校验与防重复点击标记**；
- `danger = MEDIUM`、非 `parallelSafe`；CHAT 不广告、ACT 逐次确认、
  MAX 可自动、无人值守 HIGH 规则不变。

### 6.5 模板制作流程

1. `take_screenshot` 或 a11y 截图取帧，产物在 `tests/tempImg/`；
2. PC 侧裁切图标（保留必要 padding，透明背景存 PNG-32）；
3. 按命名规范放入 `app/src/main/assets/rpa_templates/<app>/`；
4. 用调试页（P2 可做）在当前屏幕实测分数，分数入台账注释。

## 7. assists 无障碍封装的采用策略

不替换、不并行，**增量增强**，经 app 层 `AssistsGateway` 单点收口：

- **阶段一（本方案）**：继承 `AssistsService` 完成合体与初始化；OpenCV 落地；
  现有动作仍走 `AccessibilityBridge`。
- **阶段二（后续单独立项）**：按需把 bridge 欠缺的能力平移为增强接口，候选：
  - 按 **resource-id / className / 可点击属性**的结构化选择器
    （配置里 `flagReportViewIds` 已开，只差读取与 JSON 树输出）；
  - 节点直接动作（click 父节点链）减少坐标手势依赖；
  - 无障碍**事件驱动等待**（现服务 `onAccessibilityEvent` 为空实现，
    `wait_for` 靠 400ms 轮询；assists 监听器可直接提供事件流）；
  - 步骤器（stepper/stepper2）仅作参考，编排仍归我方 AgentLoop，不引入第二大脑。
