## 0. 一句话

**需求一给每条「问到我方隐私」的来信加一道联系人级决策闸门（默认交主人，可绕行+汇报）；
需求二把聊天中值得记住的事实沉淀成可查看、可检索、可更新、可理解的结构化记忆。**
两件事共享同一套行业底座的隐私分类学：闸门决定「**能不能说**」，记忆决定
「**记不记得住**」，敏感分级决定「**给谁看**」——代言 LLM 永远拿不到 secret，
参谋 LLM 按需拿到并只产给主人的建议（纵深五层 + 双通道，§3.6/§4.4）。

---

## 1. 需求原文要点（用户口径）

1. 正常聊天回复中增加**敏感/隐私信息的决策闸门**：对方问年纪、身份证号、婚否、
   存款、孩子、商业机密、身体状况、社会关系、财产、个人感情、政治态度、对真实
   事件的态度等——系统不能直接回答或表态；**有时交给用户接管回复，有时 LLM 继续
   聊但不正面回答**。联系人级「隐私策略」两档：
   **① 交给主人回复（默认）② 绕行继续聊天并汇报给主人**。
2. 聊天中的重要信息要记住并沉淀：对方给的电话、姓名、身体情况、习惯、爱好、
   对事件的看法态度、需求、愿望、计划行动；**主人接管亲笔回复的内容**（如报出的
   身份证号）系统也要记住。这些记忆点要能**查看、检索、更新、理解**。
   优先考虑使用 NovaBAIC 原框架的记忆功能。

## 2. 与既有系统的关系（复用优先，不造轮子）

| 既有设施 | 现状 | 本方案怎么用 |
| --- | --- | --- |
| E1 接管链（HandoffRules/HandoffGate/EscalationNotifier/await-human） | 已实装 | 隐私闸门**复用整条链**：PRIVACY 已是接管四类之一；新增九域细分与 bypass 档，不重写通报/挂起 |
| HandoffGate 轻 LLM 主判定（≤120tok/8s，每后台来信一次） | 已实装 | **合并升级**为来信分类器，一次调用同时产出 handoff 与 privacy 九域——不增加每来信 LLM 成本 |
| Gatekeeper 自动档硬审（含「敏感隐私」AUTO_REGEXES） | M3 已实装 | 最后一道兜底不变：bypass 档生成的回复若仍含敏感实质内容，发送前拦下降起草 |
| PersonaExtractor 画像萃取（慢车道、everyTurns 节流、草稿 ✓/✕） | 已实装 | 事实沉淀的**主捕获通道**：萃取 prompt 增加事实抽取段，复用节流与互斥锁 |
| PersonaSchema 字段目录（assets JSON 驱动萃取/表单/渲染） | 已实装 | 事实 kind 目录同构复用该机制；新增事实类型只改 JSON |
| 上游 MemoryRepository（addNote/recall/**recallByEntity**/MemoryText） | 上游能力 | **双层记忆的通用层**：非敏感通用事实可选镜像 addNote（挂联系人实体名，recallByEntity 可召回）；MemoryText.terms/normalize 纯函数直接复用做指纹归一化 |
| 画像页（AdvisorPage 骨架、草稿核阅通道） | 已实装 | 事实记忆的查看/编辑/删除 UI 挂画像页新分区 |
| director_logs 台账 + 周报对账（DirectorLedgerStats） | 已实装 | 隐私命中与事实增长进周报（E2 对账口径延伸） |

**为什么不把全部事实塞进上游记忆**：上游记忆是全局自由文本池+评分召回，没有
per-contact 绑定、没有敏感分级、没有回放链（sourceTurnId）、没有画像页管理面。
好参谋需要的是「某联系人的结构化档案」——故自建 `contact_facts` 主存储，
上游记忆做通用层镜像（可选）。

## 3. 需求一：隐私闸门（PrivacyGate）

### 3.1 隐私分类学（行业映射十二域 + 中性域，词表与 LLM 分类共用）

**不以用户举例为界，以现行标准为底座**：中国《个人信息保护法（PIPL）》第 28 条
敏感个人信息范围、《GB/T 35273-2020 个人信息安全规范》的信息类型划分、
GDPR 第 9 条特殊类别数据，再加聊天代言场景特有的两类高危项。每域标注依据
与默认敏感档（域≠档，域是内容分类、档是处理等级，§4.4）：

| # | 域 | 覆盖内容 | 标准依据 | 默认档 |
| --- | --- | --- | --- | --- |
| P1 | 身份凭证 | 身份证号/护照/驾照/银行卡号/密码/验证码 | GB/T 35273 敏感个人信息 | secret |
| P2 | 健康身体 | 疾病/体检/身体特征/生物识别 | PIPL 医疗健康、GDPR Art.9 health | secret |
| P3 | 财产金融 | 存款/收入/资产负债/金融账户/报价底线预算 | PIPL 金融账户、GB/T 个人财产信息 | secret |
| P4 | 精确行踪 | 实时位置/家庭住址/常去地点/出行计划 | PIPL 行踪轨迹 | secret |
| P5 | 信仰政治 | 宗教信仰/政治观点/党派倾向 | GDPR Art.9、PIPL 宗教信仰 | secret |
| P6 | 未成年人 | 对方提及的未成年人的一切信息 | PIPL 特别保护（不满十四周岁） | secret |
| P7 | 亲密私生活 | 恋爱史/性生活/私密关系细节 | GDPR Art.9 sex life | secret |
| P8 | 身份属性 | 姓名/生日/年龄/婚姻/子女/职业学历 | GB/T 个人基本信息 | masked |
| P9 | 联系方式 | 电话/城市/工作单位 | GB/T 个人通讯信息 | masked |
| P10 | 社会关系 | 家庭构成/领导同事评价/社交圈恩怨 | GB/T 联系人信息 | masked |
| P11 | 商业机密 | 内部价格/成本/客户资料/未公开计划 | 商业秘密三要件（秘密性/价值性/保密措施） | secret |
| P12 | 立场表态 | 对真实事件与人物的态度评价/我方立场 | GDPR Art.9 political opinions（映射） | secret |
| N0 | 中性事实 | 爱好/习惯/需求/愿望/计划/共同经历 | 非个人信息（记忆主战场，不设防） | normal |

要点：
- **P12 立场表态单列**：泄露代价是名誉与关系而非财产，且系统「不能代用户表态」
  是绝对红线——bypass 回避段对该域最强硬（倾听、反问、转移，绝不代答）。
- **P11 商业机密**双向设防：对方问报价底线（我方机密外泄）；主人闲聊说出客户
  名单（对方记录）——闸门两侧都拦。
- **档位用户可调**：域决定默认档，画像页可把单条事实调档（如把闺蜜的生日从
  masked 调成 normal 让代言 LLM 知道可以祝寿）。
- **开放兜底**：LLM 分类不限于十二域——「其他敏感项」也输出 privacy=true
  （domain=other），宁误报不漏报；词表与例句库随周报持续扩枚举。

### 3.2 联系人级策略（contact_profiles 加一列，TEXT 零迁移）

`privacyPolicy: String = "handoff"`，两档：

| 档 | 行为 |
| --- | --- |
| `handoff`（**默认**） | 命中十二域任一 → 走 E1 接管链：铃声通报 + await-human 挂起 + 抑制 AI 草稿，**答案必须主人亲笔** |
| `bypass` | 命中 → LLM **继续聊但回避该域**（生成端注入域定制回避段），同时**轻通报主人**「对方问了 XX，已绕行」；台账落 `privacy_bypass` |

> 默认 handoff 的理由：十二域里大半（证件/财产/健康/立场）答错代价不对称——
> 宁可多打扰，不可说错话。bypass 适合闺蜜级亲近联系人与纯闲聊对象。

### 3.3 判定链（合并分类，成本零增量）

```
后台来信 ──白名单快筛(纯应答, skip)──► 无事发生
   │
   ├─ 强模式词表（PrivacyRules.strongHit：九域共现正则，一票否决）──► 命中=privacy(domain)
   │
   └─ 轻LLM 来信分类器（HandoffGate 升级，一次调用）：
        输出 { handoff: bool, category?, privacy: bool, privacyDomain? }
        超时/畸形 → null（uncertain，按总闸宽松/严格档处置，与 E1 同款）
```

- **词表优先级**：PrivacyRules.strongHit 命中即 bypass/handoff，不再受 LLM 结果
  反向覆盖（宁严勿松，与 E1 的 strong-override 同构）。
- **uncertain 语义**：宽松=不判隐私、放行；严格=视同 handoff 通报。复用 E1 的
  `escalationStrict` 开关，不新增设置项。
- **生效范围与 E1 同口径**：仅后台回合（通知驱动/自动托管）；主人手动分屏在场
  时不拦截（人在看，自己把关）。

### 3.4 执行面

| 档 | 生成端 | 通报端 | 台账 |
| --- | --- | --- | --- |
| handoff | 无回复（挂起等主人） | E1 notifyHandoff（铃声+全屏横幅，domain 作副标题） | ROUTE_HANDOFF / escalation_notified |
| bypass | customSystemPrompt 注入 `PrivacyAvoidSection(domain)`：明确「不提供、不确认、不表态，自然带过并反问对方」 | **轻通报**（同渠道、IMPORTANCE_DEFAULT、无全屏意图、无铃声）——主人在忙不被每次全屏打断，回头看通知即可 | ROUTE_REPLY / `privacy_bypass`（带 domain） |

- `PrivacyAvoidSection` 十二域各一段约束文案（常量，同 HANDOFF_AVOID_SECTION 通道，
  插在 autoDirectiveSection 之后）。
- **兜底**：bypass 档生成的回复在自动档发送前仍过 Gatekeeper「敏感隐私」硬审；
  起草档则本来就要主人一键发，天然安全。
- **自问自答防线**：主动保温（TopicEngine）与自动档 system prompt 的 forbidden
  列表追加「不主动透露隐私域内容」（M3 同款追加，一处常量两处消费）。

### 3.5 汇报给主人的沉淀闭环

bypass/handoff 命中都落台账 → 周报对账（E2 口径）追加：十二域命中分布、bypass
次数、某联系人连续多回合被问隐私（=对方在套话，周报里显性提示）。

### 3.6 PrivacyGuard 纵深五层（回答「要不要强力 rules 防未授权泄露」：要，且单点规则必被绕过，必须纵深）

```
L1 存储层    secret 正文存 detail、content 恒掩码；全部本地 Room，零出站
L2 上下文层  ★Prompt Firewall（本方案核心 rule）★
             代言链路 system prompt 的唯一事实注入口是 FactRenderer.renderForReply()，
             内部硬规则：secret 一票拒绝、masked 强制掩码形态——任何调用方想绕过
             只能不改这个函数；配套单测锁死（喂 secret 输入，断言输出不含全文）
L3 路由层    隐私闸门（handoff/bypass）+ PrivacyAvoidSection 按域回避
L4 生成发送  生成端 forbidden 追加「不主动透露」+ Gatekeeper 发送前「敏感隐私」硬审
L5 审计层    台账 reason 键 + 周报九域命中分布 + 泄露回归单测（L2 的锁）
```

- 五层各司其职、互为备份：单层的词表漏判由 L2 的结构隔离兜底（LLM 上下文里
  根本没有 secret，模型「想泄露也无处可泄」）；L2 被未来代码误破坏由 L5 单测
  当场红。
- **Prompt Firewall 是「强力 rule」的落点**：不靠散落在各处的 if 判断隐私，
  而是把「秘密能否进入代言上下文」收敛到一个纯函数一个出口，可测试、可审计、
  合并上游时冲突面最小。

## 4. 需求二：事实记忆沉淀（contact_facts）

### 4.1 表设计（advisor.db v10 → v11，幂等迁移）

```sql
CREATE TABLE contact_facts (
    id INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
    contactId INTEGER NOT NULL,          -- 绑定联系人
    domain TEXT NOT NULL,                -- 九域 code 或 neutral
    kind TEXT NOT NULL,                  -- 事实类型（字段目录 JSON 定义）
    content TEXT NOT NULL,               -- 事实正文（secret 档存掩码化正文）
    detail TEXT,                         -- 完整正文（secret 档才有，见 §4.4）
    fingerprint TEXT NOT NULL,           -- MemoryText.normalize+terms 归一化指纹
    sensitivity TEXT NOT NULL,           -- normal / masked / secret
    sourceRole TEXT NOT NULL,            -- incoming / outgoing（我方亲笔）
    sourceTurnId INTEGER,                -- 回放链锚点（E1 turnMessageId 同构）
    createdAt INTEGER NOT NULL,
    updatedAt INTEGER NOT NULL,
    deletedAt INTEGER,                   -- 软删除
    INDEX(contactId), INDEX(fingerprint)
)
```

**fingerprint UNIQUE + 同指纹更新**：同一条事实重复出现 → 更新 updatedAt 与
detail、不新增行（复用上游 addNote 的去重/合并思想，本地简化版）。
冲突裁决：incoming 与 outgoing 说法矛盾 → 新胜旧，旧行软删保留可回看。

### 4.2 kind 字段目录（assets JSON，PersonaSchema 同构）

`advisor/fact_schema.json`：kind code、中文名、九域归属、prompt 抽取说明、
编辑表单控件类型。新增事实类型**只改 JSON 不改表**。首批 kind：

```
姓名称呼 / 联系电话 / 居住城市 / 身体状况 / 习惯偏好 / 兴趣爱好 /
观点态度（事件+立场）/ 需求愿望 / 计划行动 / 重要日期（生日纪念日）/
关系事件（何时认识/共同经历） / 我方档案（主人亲笔给出的事实）
```

### 4.3 三源捕获

| 源 | 时机 | 通道 | 成本 |
| --- | --- | --- | --- |
| ① 画像萃取扩展（主通道） | 每 extractEveryTurns 回合一次（节流与互斥锁现成） | PersonaExtractor 慢车道 prompt 追加事实抽取段，输出 facts JSON 数组，与画像字段同次 LLM 调用产出 | **0 次新增 LLM** |
| ② 主人亲笔捕获（OUTGOING） | submitTurn 手动发言后触发一次定向抽取（60s 节流） | 只喂本轮我方回复+屏文，轻 LLM ≤300tok；用户明确要求：报出的身份证号这类要立刻记住 | 每次手动发言后至多 1 次（节流内） |
| ③ 对方来信事实（INCOMING） | 已被①覆盖（screenContent 含对方消息） | — | 0 |

- 抽取输出走**宽松解析**（HandoffGate/ActionPlanner 同款）：畸形即丢弃不重试，
  不影响参谋主链。
- 高频互斥：②与①共用 PersonaExtractor 的互斥锁（历史教训：并发重复萃取烧 token）。

### 4.4 敏感分级 × 双通道消费（v2 核心修订：回答「secret 记住了怎么用」）

**LLM 有两个消费面，安全属性完全不同**：

- **代言上下文（Reply Channel）**：生成「发给对方的消息」的 system prompt 常驻注入——
  一旦注入就可能被模型说出去，是泄露面；
- **参谋上下文（Counsel Channel）**：给主人看的分析/建议/简报的一次性调用注入——
  产物只在本地展示给主人，**绝不回流会话历史、绝不成为发送候选**。

由此得到双通道矩阵（取代 v1 的「secret 永不进 LLM」一刀切）：

| sensitivity | 存储 | 画像页展示 | 代言上下文（发给对方） | 参谋上下文（给主人看） |
| --- | --- | --- | --- | --- |
| normal | 明文 | 明文 | 明文注入 | 明文 |
| masked | 明文 | 掩码显示（138\*\*\*\*5678），点按显全文 | **掩码形态注入**（LLM 知道有此事实、不知全文 → 会正确回避/交接） | 明文 |
| secret | content 存掩码、detail 存全文 | 默认只显掩码 | **永不注入**（Prompt Firewall L2 硬规则） | **按需注入，参与分析** |

**secret 档记住了的意义——三个使用出口**：

1. **行动面检点（FactScheduler，主动建议）**：复用 M2-b 的 AlarmManager 单班闹钟
   周期检点，每日一次扫描日期型事实（生日/纪念日/约定日）与待办型事实（计划/
   愿望）——命中「明天=张三生日」→ 组装一次参谋分析调用（此时才把生日事实
   注入该次调用，主人视角明文，≤400tok）→ 产出行动建议「明天是他的生日，
   建议送花/祝寿，话术草稿：…」→ 走**给主人的通道**（GoalTab 行动提示卡/通知，
   E1 ACTION_SHOW_ESCALATION 同款拉起画像页）。
2. **参谋问答（Counsel Q&A）**：主人在分屏问「他生日什么时候来着」→ 按联系人
   检索 contact_facts → 命中事实临时注入一次参谋调用 → 回答只显示给主人。
3. **周报与画像理解**：BriefCompiler 周报与画像萃取把事实作为分析素材
   （secret 以脱敏口径参与，如「本月你向 X 透露过证件信息」——不复述全文）。

**给主人的产物流回代言链路的唯一出口是主人手动**（自己打字/自己复制）——系统
不提供任何把参谋产物一键转发送候选的路径，与 M2 起草档「人肉一键发」纪律一致。

> 完整回答用户的生日之问：「LLM 是如何知道明天是他的生日？生日信息是事先必须
> 发给 LLM 吗？」——**不是事先常驻注入**。代言 LLM 日常聊天里不知道生日
> （masked 掩码形态），对方问起时只会正确绕行；「明天是生日」由 App 侧确定性
> 检点（不花 LLM）发现，在产出建议的那一刻才把生日临时告诉参谋 LLM，产物
> 仅主人可见。确定性的事实由代码消费，语言性的建议才交给模型。

### 4.5 查看 / 检索 / 更新 / 理解

- **查看/更新**：画像页新增「事实记忆」分区（AdvisorPage 骨架铁律）：按域分组
  列表、敏感项掩码、可编辑/删除/改敏感性；与画像字段草稿同一核阅风格。
- **检索**：contact_facts 建 FTS4 索引（AdvisorEntities 有先例）；分屏「纯问答」
  模式支持跨联系人查询（「谁提过周五见面」）；单联系人自动注入无需检索。
- **理解（注入渲染）**：代言链路事实段由 FactRenderer.renderForReply() 产出
  （Prompt Firewall L2，唯一注入口）——按域分组、按 updatedAt 优先、normal 全显/
  masked 掩码/secret 拒绝；总长度截断（facts 段 ≤400 字，超出按近因截断）。
  参谋链路（检点/问答/周报）走 renderForCounsel()：masked/secret 以主人视角
  明文参与分析。这保证对方追问「上次说的号码再报一遍」时代言 LLM 知道有这个
  事实并正确绕行/交接，而不是编造或背出来。
- **上游记忆镜像（可选，默认开）**：normal 档事实落库同时 `MemoryRepository.addNote`
  挂联系人实体名（recallByEntity 可召回），让主界面全功能 AgentLoop 的记忆检索
  也能命中；masked/secret **不镜像**（上游池无敏感分级）。设置页总开关 +
  AdvisorPrefs 字段。
