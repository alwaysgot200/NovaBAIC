## 0. 为什么需要这个模式

现状：ScreenAdvisor 是 2500+ 行的「大脑」，所有专家职能（路由/接管判定/画像
萃取/守门/通报）以方法或字段形式长在它身上——每加一个专家就注入一个类、
加一段编排代码，上帝类持续膨胀，专家职责散落。

现代 agent 子代理的组织特征（专家人隐喻 → 本地落地）：

| 子代理特征 | 本地工程对应 |
| --- | --- |
| 每个代理 = 角色人设 + 专属工具 + 上下文预算 | 一个自包含包：词表/例句/LLM 配置/裁决全在内 |
| 代理间只传结构化结论，不共享思考过程 | Verdict（结论+理由码+证据），编排器只读裁决 |
| 编排器只分发不干活 | ScreenAdvisor 只问合议团一次 |
| 代理互不调用，通信经编排器 | 专家包之间禁止 import |
| 每个代理有独立模型/温度/例句配置 | LLM 配置收敛为专家内部常量 |

## 1. 专家五件套（每个专家一个包）

```
floatball/experts/<expert_name>/
  ├── <Name>Verdict.kt    # 结构化裁决：结论 + reason 码 + 证据（data class）
  ├── <Name>Rules.kt      # 经验法则：词表/强模式/阈值（纯函数，JVM 单测）
  ├── <Name>Gate.kt       # 直觉判断：轻 LLM 分类器（≤N tok/超时/温度收敛）
  │                       #   —— 需要 LLM 泛化时才有；纯词表专家可无此件
  ├── <Name>Assets.kt     # few-shot 例句库/文案常量（或 assets JSON）
  └── （test/）<Name>Test.kt  # 经验法则回归 + 泄露/越界锁测试
```

人设注释铁律：每个专家包根文件顶部用 KDoc 写「这个专家是谁、只管什么、
不管什么」——如同给新同事的岗位说明书。

## 2. 专家名录（现有映射 + 新增）

| 专家 | 人设一句话 | 现状 | 落位 |
| --- | --- | --- | --- |
| Director 调度长 | 「本轮该干什么」 | director/（路由表纯函数） | 原地（编排器本人） |
| Gatekeeper 守门人 | 「发出去的话踩不踩红线」 | auto/（AUTO_REGEXES+轻LLM审） | 原地 |
| Handoff 交接官 | 「这话是不是只有主人能答」 | director/Handoff*（E1） | 原地，暂不迁包 |
| **Privacy 隐私专员** | 「这话/这稿碰不碰隐私红线，怎么绕」 | 新增（F1） | **experts/privacy/** |
| **Archivist 档案员** | 「什么值得记、记成什么级」 | 新增（F2） | **experts/facts/** |
| Persona 画像师 | 「对方是什么样的人」 | PersonaExtractor+Schema | 原地 |
| Strategist 战略参谋 | 「目标推进到哪一步」 | mission/Judge 链 | 原地 |
| Stylist 风格师 | 「怎么说话像主人」 | style 链 | 原地 |
| Topic 话题策划 | 「聊什么不冷场」 | TopicEngine | 原地 |
| Liaison 联络官 | 「怎么把消息送达主人」 | notify/EscalationNotifier | 原地（执行面非专家） |

**渐进收敛原则**：新专家一律进 `experts/<name>/`；存量专家原地保留不迁包
（避免为架构洁癖制造大 diff 与合并冲突），仅当某存量包因需求自然改动时顺势
补五件套结构注释。

## 3. ExpertPanel 合议团（本次模式的核心新增）

专家越来越多，ScreenAdvisor 不该逐个调用——**合议团是唯一对编排器暴露的
专家门面**：

```kotlin
@Singleton
class ExpertPanel @Inject constructor(
    private val handoffExpert: HandoffExpert,   // 包装现有 Rules+Gate
    private val privacyExpert: PrivacyExpert,
    // 后续专家在此登记
) {
    /**
     * 后台来信合议：全部来信向专家并行征询，合并成一份会审结论。
     * 成本纪律：N 个专家 ≠ N 次 LLM——共享一次轻 LLM 分类调用
     * （各专家词表先行直判，LLM 对未直判部分一次产出多域结论）。
     */
    suspend fun reviewIncoming(cue: IncomingCue): IncomingReview
}

data class IncomingReview(
    val handoff: HandoffVerdict,
    val privacy: PrivacyVerdict,
    // 未来：sentiment? risk? —— 每个新专家在这里加一个字段
)
```

- **合议纪律**：专家裁决 OR 合并（宁严勿松，与 E1 同构）；任一专家故障只降级
  自己的结论，不拖垮合议（runCatching 包裹，故障走词表备胎）。
- **执行面不进合议团**：Liaison（通知）、ActionDispatcher（发送）、Gatekeeper
  L4 兜底都是「手」不是「脑」，保持在原层——专家只动嘴（裁决），不动手。

## 4. ScreenAdvisor 瘦身路径

1. `judgeEscalation()` 的判定段迁入 ExpertPanel（E1 行为等价重构，理由码不变）；
2. 后续每个新专家 = experts 包 + Panel 登记一行 + 消费 Verdict 一小段——
   ScreenAdvisor 净增代码趋近于零；
3. 编排器只保留：会话/记忆/LLM 管道 + 顺序控制 + 裁决消费。

## 5. F1 按本模式的落地蓝图

```
experts/privacy/
  PrivacyVerdict.kt     # 域/档/bypass|handoff/理由码
  PrivacyDomain.kt      # 十二域+默认档映射（§3.1 行业底座）
  PrivacyRules.kt       # 域词表 strongHit（纯函数）
  PrivacyExpert.kt      # 合议内裁决：词表直判 ∪ 分类器结论
  PrivacyAssets.kt      # 十二域回避文案 + few-shot 例句
experts/handoff/ 不新建——HandoffExpert 薄包装放 ExpertPanel 同文件
```

单测重点：PrivacyRulesTest、泄露锁（renderForReply 喂 secret 断言无全文）、
Panel 合并（LLM 故障降级不拖垮 handoff 裁决）。

## 6. 组织铁律（并入开发纪律）

1. 专家包之间禁止 import（共享领域模型除外）；通信只经 Verdict/Panel。
2. 专家内不做执行动作（不发通知、不写库、不发送）——只出 Verdict。
3. 每专家 LLM 预算常量化（maxTokens/timeout/temperature），新专家默认 ≤300tok/8s。
4. Verdict 必带 reason 码进台账（可回放）。
5. 新增能力先问「这是新专家还是现有专家的新判据」——是判据就进现有包，
   不许另起炉灶。
