# 2026-10-29 微信摘树解锁与触摸探索事故复盘方案

> **一句话结论**：微信 8.x 摘树解锁的唯一放行条件是「启用的无障碍服务列表里有
> TalkBack 家族（marvin）服务」；解锁落地为 `WechatTreeUnlock`（分析会话级临时
> 启用「随选朗读」）。触摸探索常开、autojs 白名单桩两条路线均实测无效且各自
> 闯过祸——全部禁用/弃用，坑因沉淀见 `AGENTS.md` §8 教训 11。
>
> 关联文档：[`2026-10-27-悬浮菜单RPA入口与三工具交互方案.md`](2026-10-27-悬浮菜单RPA入口与三工具交互方案.md)
> §7.14.3（复核修正块为该节现行结论）；本文是当日全部取证、事故与运维 SOP 的
> 独立复盘，供后续排障与新功能设计对照。

## 1. 问题域

好参谋 RPA 的 a11y 线需要读微信界面节点树（布局分析器、`RpaSelector` 定位）。
微信 8.0.79（Redmi 23077RABDC / HyperOS OS2.0.205.0 / Android 15）存在主动
反自动化：`smartDisableAccessibility`（`com.tencent.mm.sdk.platformtools.b.c()`）
在不满足放行条件时反射 `AccessibilityManager.setStateLocked(0)` 关闭自身进程的
无障碍，任意页面 `rootInActiveWindow` 只剩空根（`uiautomator dump` 恒 381 字节）。

同期为解锁此问题尝试的两条路线分别引发了**触摸探索常开性能事故**与**白名单桩
无效弯路**，并伴随若干「看似生效实则无效」的假过现象，一并复盘。

---

## 2. 事故一：触摸探索（TE）常开性能事故（2026-10-29）

| 项 | 内容 |
| --- | --- |
| 起因 | 推测 TE=true 能让微信放行（dex 静态取证的条件之一是 `isTouchExplorationEnabled`），把 `flagRequestTouchExplorationMode` 静态写进 `accessibility_service_config.xml` |
| 症状 | 触摸探索随服务绑定常开：**全机触摸变「先探索后激活」**、单指拖动被吃掉、悬浮球拖不动、系统明显卡顿（用户原话：「运行的特别的慢，悬浮图标都拖不动」） |
| 根因 | 该 flag 的语义是「服务绑定即请求触摸探索模式」，是全局触摸模式而非服务私有能力；照抄 AssistsX 的常开配置直接把整机触摸体验打穿 |
| 修复 | 从服务配置删除该 flag；运行时 `setServiceInfo` 脉冲方案（`TouchExplorationGate`）在 HyperOS 上是空操作，仅留作不可用兜底 |
| 禁令 | **【禁止】把 `flagRequestTouchExplorationMode` 静态写进任何服务配置**（AGENTS.md §8 教训 11 固化） |

> 补充事故二（同日）：高频触发 `settings delete/put enabled_accessibility_services`
> 或反复重绑 a11y 服务，会让**系统全部无障碍服务解绑重绑**（整机约 1s 卡顿），
> 也是卡顿元凶之一。修复：`FloatBallService.rebindA11yService` 加 10 秒冷却节流；
> `WechatTreeUnlock` 只包住分析会话（acquire/release 配对），不做周期性写入。

## 3. 微信摘树解锁演进（时间线与被推翻的结论）

### 3.1 dex 静态取证结论（后被推翻）

反编译 `classes8.dex` 的 `smartDisableAccessibility` 得到两条件：

1. `getEnabledAccessibilityServiceList(FEEDBACK_SPOKEN)` 含微信可信白名单组件
   （`HashSet` 18 条固定 ID，含
   `org.autojs.autojs/com.stardust.autojs.core.accessibility.AccessibilityService`）→ 放行；
2. 否则 `isTouchExplorationEnabled()==true` → 放行；
3. 否则摘树（381 字节空根）。

据此走了两条弯路：

- **白名单桩路线**：构建 `org.autojs.autojs` 白名单桩 APK
  （`dev/build-a11y-whitelist-stub.ps1`，已删除）安装并启用，指望桩组件 ID 命中
  白名单 → **真机实测无效**（+桩仍 381 空根）。
- **feedbackSpoken 一行修复**：好参谋服务 `accessibilityFeedbackType` 只声明了
  `feedbackGeneric`，而微信查的是 `FEEDBACK_SPOKEN` 过滤——补齐为
  `feedbackSpoken|feedbackGeneric` 后 dumpsys 确认解析生效
  （`feedbackType[FEEDBACK_SPOKEN, FEEDBACK_GENERIC]`），**但微信树仍 381 空根**。

### 3.2 白名单语义反转真相

以上两条失效的共同解释：**dex 静态取证的条件在运行时并不成立**。微信经 Tinker
热补丁（logcat artd 证实加载 `patch-5a32c721`）改写了检查逻辑——静态反编译看到的
白名单匹配/TE 判断是被热修前的旧代码。

**方法论教训（假过教训之一）**：静态取证结论必须真机 A/B 复核，且 A/B 一次只动
一个变量；「dumpsys 显示配置生效」≠「目标 App 行为生效」（feedbackSpoken 就是
dumpsys 通过、功能仍空的典型假过）。

### 3.3 真机 A/B 定案矩阵

同一微信进程内逐项开合（`uiautomator dump` 采微信前台窗口，秒级实时生效）：

| 启用配置 | TE | 结果 |
| --- | --- | --- |
| 仅好参谋 | false | 381 字节空根（摘树） |
| +autojs 白名单桩 | false | 381 字节空根（摘树） |
| +桩且框架 touchExplorationEnabled=true | true | 381 字节空根（摘树） |
| **+「随选朗读」SelectToSpeak** | **false** | **92,695 字节 / 272 节点全树（含「通讯录」）** |
| +TalkBack | true | 94,354 字节 / 277 节点全树 |

**定论：放行条件唯一 = 启用列表里存在 TalkBack 家族服务
（`com.google.android.marvin.talkback/*`），与触摸探索状态完全无关。**
10-28 记录的「TE=true → 全树」里真正起作用的是当时启用列表里出现了 marvin 服务，
TE 只是伴随变量——TE 因果归因系错误。

## 4. 落地：`WechatTreeUnlock`（唯一解锁入口）

位置：`app/src/main/java/com/verlintas/baic2/floatball/auto/WechatTreeUnlock.kt`。

- **载体选「随选朗读」**：TalkBack 家族里副作用最小的服务——不开触摸探索、
  不朗读全文、无常驻浮窗；
- **会话级配对**：分析覆盖层 `[acquire]` 启用、`[release]`/`onClosed` 还原，
  只追加/移除随选朗读一个组件，用户启用的其它服务原样保留，用户自开的
  TalkBack 家族服务永不代关；
- **快路径零副作用**：树可读、或用户已开家族服务（微信本就放行）时不写任何设置；
- **失败就地回滚**：写入未生效/树仍未恢复即还原并返回 `Failed(reason)`，
  调用方 toast 报因引导手动开启「随选朗读」，不静默失效（§4.5 严禁静默失效）；
- **写设置后等待重绑**：`pollA11yReady` 等自身服务回归再采集（写
  `enabled_accessibility_services` 会触发全部 a11y 服务解绑重绑，约 1s）；
- `TouchExplorationGate` 降级为树退化兜底（HyperOS 运行时 `setServiceInfo`
  是空操作，实际不可用）；解锁不可用的场景走 `VISION` 线，
  `DUAL` 依赖定位 miss 后显式 `LineFallback` 切线，不静默换线。

## 5. 坑录（排障对照表）

### 5.1 meta-data 键名坑

自建无障碍服务（白名单桩时代踩过）声明服务配置时，Manifest 里挂配置的
`<meta-data>` 键名必须是 **`android.accessibilityservice`**（指向服务配置 xml
资源）。键名写错时系统**静默忽略**配置：服务照常绑定、`dumpsys` 里却看不到
预期的 flags/capabilities，极易与「微信摘树」混淆排查。同理，`settings put
enabled_accessibility_services` 写入的组件串必须是 `包名/类全名` 且逐字符匹配
（如好参谋：
`com.verlintas.baic2/com.verlintas.baic2.device.impl.a11y.Baic2AccessibilityService`），
微信白名单比对的也是完整组件 ID 字符串。

### 5.2 假过教训（现象 ≠ 生效）

| 假过现象 | 真相 |
| --- | --- |
| dumpsys 显示 `feedbackType[FEEDBACK_SPOKEN, …]` 解析生效 | 微信放行逻辑被 Tinker 热补丁改写，该修复对摘树无效 |
| 白名单桩安装启用、组件 ID 命中 dex 白名单 | 运行时白名单语义已反转，实测仍 381 空根 |
| 「TE=true 时树恢复」 | 起作用的是当时启用列表里的 marvin 服务，TE 是伴随变量 |
| 分析覆盖层开着时 `uiautomator dump` 仍是 381 空根 | **UiAutomation 连接会 detach a11y 服务** → 分析器自动收起 + 微信回摘树，是取证动作污染了被测状态，不是功能坏 |

**取证纪律**：分析覆盖层打开期间**严禁 `uiautomator dump`**，只用 `screencap` +
像素统计；A/B 一次只动一个变量；`dumpsys window` 的 `mAttrs.y` 与实绘差 104px
状态栏 inset，驱动坐标以 screencap 像素为准。

### 5.3 MIUI/HyperOS USB 安装弹窗 SOP

1. 开发者选项必须开「**USB 安装**」，否则 HyperOS 直接拦截侧载（安全中心弹窗，
   无绕过手段）；
2. **同签名覆盖升级（`adb install -r`）通常免弹窗**；全新安装会弹「安装确认」
   对话框——脚本化时可抢点确认按钮（实测约 `tap 311 2250`，随分辨率/主题变化，
   先 `uiautomator dump` 校准坐标），或手动点一次；
3. `install -r` 与 `force-stop` 都会**清空 `enabled_accessibility_services`**，
   且 App 进程不存在时 `settings put` 也会被清。恢复顺序固定（AGENTS.md §8.6）：
   **先 monkey/am 拉起 App，进程活着时再 `settings put`**；
4. a11y 服务被清的表现是「已启用但未连接」提示卡片（`showAnalyzeA11yNotice`），
   优先用「重试连接」（Shizuku shell 重写配置触发重绑）自愈，勿手动反复关开
   无障碍（重绑定整机卡顿，见 §2 事故二）。

### 5.4 adb 注入三分法（浮窗/Compose 场景）

`input tap` = 普通 View click；`input motionevent DOWN/UP` = GestureDetector/Compose
`detectTapGestures` 单击（实测 Dock 触发器等 Compose 手势节点用 `tap` 不生效）；
`input swipe` 会触发扇形拖拽 bug，**禁用于浮窗**。

## 6. 禁令与红线汇总

| # | 禁令 | 后果/出处 |
| --- | --- | --- |
| 1 | 静态写 `flagRequestTouchExplorationMode` 进服务配置 | 全机触摸「先探索后激活」+ 卡顿（§2 事故） |
| 2 | 高频 `settings delete/put` / 反复重绑 a11y 服务 | 全部服务解绑重绑，整机卡顿（§2 事故二） |
| 3 | 分析覆盖层打开期间 `uiautomator dump` | detach a11y 服务，分析器收起 + 微信回摘树，误判功能坏（§5.2） |
| 4 | 静态取证结论未经真机 A/B 直接采信 | Tinker 热补丁会改写检查逻辑（§3.2） |
| 5 | 解锁通道失败后静默走空 | 必须 `Failed(reason)` 报因并引导手动开启（§4.5） |
