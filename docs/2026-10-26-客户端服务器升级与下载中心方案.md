# 好参谋客户端服务器升级与下载中心方案

> 状态：已实施（客户端 `v0.4.0`、管理仓 `v6.7.4`，2026-10-26）
> 日期：2026-10-26
> 范围：客户端项目 `NovaBAIC`（好参谋）+ 管理仓 `autojs6_Management`（部署/下载站）
> 目标：客户端不走应用商店，全部从自有服务器检查版本、下载、覆盖升级；下载页按产品展示版本；升级后不丢账号与设置。

---

## 1. 需求与硬性约束

1. `/download/` 下载页按**产品**展示客户下载链接，并标明版本。
2. **以管理仓 `autojs6_Management` push `v*` tag（或手动 Run）为触发契机**，CI 自动拉取 `NovaBAIC` 项目最新稳定 Release，上传到生产机对应目录；只保留最新 3 个版本；版本未变则不上传。
   - `NovaBAIC` 是**独立发布**的，它的版本号与管理仓 tag 没有任何绑定关系。
   - 管理仓 tag 只负责“触发同步”，不会改写客户端版本号。
3. 好参谋 App 每次启动后在空闲时间检查服务器版本，**从左到右逐段比较**：
   - 第一段（X）小于服务器：**强制升级**（直接下载并安装，否则 App 不可用）。
   - 第一段相同、第二段（Y）小于服务器：**提示升级**（“服务器端有新版本可用”，用户决定是否升级）。
   - 第一段、第二段都相同，只有第三段（Z）小于服务器：**不提示**。
4. 升级安装后，**原有账号、设置参数必须保留，不得再次要求登录**（硬性要求）。
5. 用户下载来源必须是自有服务器 `https://autojs6.80fafa.com`，不能依赖应用商店，也不让用户跳 GitHub。

## 3. 总体设计

```
NovaBAIC 仓库独立打 tag vX.Y.Z
        │
        ▼
NovaBAIC CI 发布 Release（app-release.apk + .sha256）
        │   （与管理仓 tag 无关系，独立发生）
        │
        ▼
管理仓 push v* tag / 手动 Run（唯一同步契机）
  ├─ deploy：后端镜像 + 站点（VitePress + /admin）
  └─ publish-nova-site：查询 NovaBAIC 最新稳定 Release → 校验 → scp → 服务器落盘
        │
        ▼
https://autojs6.80fafa.com/download/
  ├─ haocanmou/manifest.json      ← App 版本检查唯一事实源
  ├─ haocanmou/v0.3.7/...apk      ← 最新 + 历史 3 版
  ├─ manifest.json                ← AutoJs6 客户端（现有，保留）
        │
        ▼
好参谋 App 启动
  └─ 读 manifest → 逐段比对版本 → 提示/强制 → 从自有服务器下载
       → 校验 SHA-256 + 签名 + versionCode → 系统安装器覆盖安装
       → 数据保留，不重新登录
```

设计原则：

- **单一事实源**：App 检查、下载页展示、CI 上传全部使用同一份 `haocanmou/manifest.json`。
- **发布解耦**：NovaBAIC 只负责产出 Release；管理仓只负责“把最新稳定 Release 同步到生产”。
- **服务器未升级，客户端不提示**：只有管理仓完成一次部署、manifest 更新后，App 才会看到新版本。
- **不新增后端接口**：版本信息是静态 JSON，由 nginx 直接服务；不引入新的 Nest 模块、权限、数据库表。
- **不新增第三方依赖**：客户端复用 Hilt 注入的 OkHttp/Json、复用系统安装器；服务端复用 nginx + python3。
- **用户只访问自有域名**：GitHub 只作为 CI 的构建产物来源，终端用户不接触 GitHub。
- **幂等**：重复部署不重复上传；版本未变直接跳过；失败可重跑。

## 4. 版本号与升级规则

### 4.1 版本格式

- 发布版本严格 `vX.Y.Z`（三段数字），`X` 主版本、`Y` 次版本、`Z` 补丁号。
- App 内 `versionName` 可能带本地/预览后缀（如 `0.3.8-dev.gabc1234`），比较时**只取 `-` 前的三段数字**。
- `versionCode` 由 release CI 按 `X*10000 + Y*100 + Z` 生成，安装层用它保证覆盖升级只增不减。

### 4.2 判定规则（最终版：从左到右逐段比较）

先做 `versionCode` 防降级兜底，再做三段比较：

| 顺序 | 条件 | 行为 |
| --- | --- | --- |
| 1 | 服务器 `versionCode <= 本机 versionCode` | 不处理（防降级/防同版重复提示） |
| 2 | 本机 `X < 服务器 X` | **强制更新**：下载并拉起安装；不更新则 App 不可用 |
| 3 | 本机 `X > 服务器 X` | 不处理（本机版本更高） |
| 4 | `X` 相同，本机 `Y < 服务器 Y` | **可选更新**：提示“服务器端有新版本可用”，用户选择立即升级/稍后 |
| 5 | `X` 相同，本机 `Y > 服务器 Y` | 不处理（本机次版本更高） |
| 6 | `X`、`Y` 都相同，本机 `Z < 服务器 Z` | **不提示**（按您的规则，第三段小不打扰用户） |
| 7 | 三段都相同 | 不处理 |
| 8 | 网络失败且无历史强制记录 | 放行，不打扰用户 |
| 9 | 网络失败但本地缓存了“强制版本”且本机仍低于它 | 继续强制拦截（防止断网绕过） |

示例：

| 本机 | 服务器 | 结果 |
| --- | --- | --- |
| `0.2.9` | `1.0.0` | 第一段 0 < 1 → 强制 |
| `0.3.7` | `0.4.0` | 第一段相同、第二段 3 < 4 → 提示 |
| `0.3.7` | `0.3.8` | 第一、二段相同、第三段 7 < 8 → **不提示** |
| `1.0.0` | `0.9.9` | 本机更高 → 不处理 |

> 这条规则不会因为补丁号递增而打扰用户；补丁版本仍会同步到下载页，用户手动下载即可。若未来希望补丁版本也提示，只需调整第 6 条。

### 4.3 关于“升级后不重登”的边界说明

本方案保证的是：**升级动作本身不再触发登录门**。只要升级时本地会话仍在有效期内，升级后直接进入原界面。
若升级发生在会话已过期之后（当前 access token 默认 1 小时，且服务端暂未实现真正的 refresh token 续期），那么即使不升级，App 启动也必须重新登录——这是既有会话策略，不是升级引入的额外登录。若要求“长期不登录”，需要另行实现 refresh token 续期（本次不扩大改动面，可在后续单独立项）。

## 5. 服务器端：拉取最新好参谋发布包并同步（需求 2）

### 5.1 关键问题：怎么可靠地拿到“最新好参谋发布包”？

`NovaBAIC` 是独立仓库、独立发布。管理仓**不重新构建**好参谋，只拉取 NovaBAIC CI 已经构建、签名、发布的正式 APK；签名与 versionCode 由 NovaBAIC 的 release 流水线唯一负责，管理仓只做同步与二次校验。管理仓部署时不能假设“自己知道最新版本”，必须每次都去**查**。取包策略按以下优先级分层，任何一层成功即可继续：

#### 第 1 层：GitHub REST API 列出正式 Release，取最高稳定 semver（主路径）

```bash
curl -fsSL \
  -H 'Accept: application/vnd.github+json' \
  -H 'X-GitHub-Api-Version: 2022-11-28' \
  'https://api.github.com/repos/alwaysgot200/NovaBAIC/releases?per_page=30'
```

- **不直接依赖 `releases/latest`**：GitHub 的 `latest` 是按“创建时间”选最新正式 Release；如果旧 tag 被后补发布，它可能压过版本号更高的 Release。我们改为拉取最近 30 个 Release，过滤后**按三段版本号取最大**（即 `versionCode` 最大）。
- 过滤条件：`draft == false`、`prerelease == false`、`tag_name` 匹配 `^v[0-9]+\.[0-9]+\.[0-9]+$`。
- 取字段：`tag_name`、`published_at`、`body`、`target_commitish`、`assets[]`（含 `name`、`size`、`browser_download_url`）。
- 为什么要用它：返回结构化资产列表，**不依赖 APK 文件名固定**；未来资产改名/多 ABI 也能按 `assets[]` 选。
- 匿名可读，已实测 `v0.3.7` 可匿名获取；每次部署只 1 次请求，不占 Actions 制品额度，也不会触发私有仓 500MB 存储问题。
- 若列表为空（还没有任何正式 Release）：**跳过 Nova 同步并告警，不阻断管理仓部署**。

校验：

- `tag_name` 必须匹配 `^v[0-9]+\.[0-9]+\.[0-9]+$`。
- `draft == false` 且 `prerelease == false`。
- 资产选择：
  - 从 `assets[]` 里取 `name` 以 `.apk` 结尾的资产；
  - 只有一个 → 直接用；
  - 多个 → 优先名字含 `arm64` 的；仍不唯一 → 直接失败并打印资产列表，绝不猜。
  - `.sha256` 资产：优先取 `<apk 文件名>.sha256`；没有则看 API 是否提供 `digest`（`sha256:...`）；两者都没有则失败。
- 记录 `repo=alwaysgot200/NovaBAIC`、`tag`、`assetName`、`releaseUrl` 到最终 manifest 的 `source` 字段，便于追溯。

#### 第 2 层：`releases/latest`（列表接口异常时兜底）

```bash
curl -fsSL \
  -H 'Accept: application/vnd.github+json' \
  https://api.github.com/repos/alwaysgot200/NovaBAIC/releases/latest
```

- GitHub 语义：最新一个非 draft、非 prerelease 的正式 Release。
- 只作为第 1 层不可用时的兜底；拿到后仍按同样的资产选择与硬校验流程处理。

#### 第 3 层：`releases/latest/download` 重定向（API 不可用时兜底）

```bash
FINAL_URL=$(curl -fsSL -o app-release.apk -w '%{url_effective}' \
  https://github.com/alwaysgot200/NovaBAIC/releases/latest/download/app-release.apk)
# FINAL_URL 形如 .../releases/download/v0.3.7/app-release.apk
TAG=$(printf '%s' "$FINAL_URL" | sed -E 's#.*/download/(v[0-9]+\.[0-9]+\.[0-9]+)/.*#\1#')
curl -fsSL -o app-release.apk.sha256 \
  https://github.com/alwaysgot200/NovaBAIC/releases/latest/download/app-release.apk.sha256
```

- 不经过 API，天然绕开匿名 API 限流。
- 依赖资产名仍为 `app-release.apk`；如果未来改名，优先回到第 1 层（API 能动态发现）。
- `published_at`/更新说明为空即可，页面/App 不因此报错。

#### 第 4 层：Releases Atom Feed（只用于拿 tag）

```bash
curl -fsSL https://github.com/alwaysgot200/NovaBAIC/releases.atom
```

- 从第一个 `<entry>` 的 `<link ... href=".../releases/tag/v0.3.7"/>` 解析 tag。
- 只把它当“tag 发现”兜底；拿到 tag 后仍按固定资产名下载 APK + `.sha256`。
- 遇到带 `-` 的预发布 tag 直接跳过；只认三段数字 tag。

> 四层策略的目的：**公开仓库不依赖任何 Secret**；API 限流时仍能取到包；同时不把“APK 文件名”写死成唯一入口。网络临时失败用 `curl` 重试；重试后仍失败则 job 红灯，便于发现。

#### 取包后必须完成的硬校验（缺一不可）

1. `sha256sum -c`：APK 与 `.sha256` 一致。
2. `aapt2 dump badging`：
   - `package name == com.verlintas.baic2`；
   - `versionName == tag 去 v`；
   - `versionCode == X*10000 + Y*100 + Z`。
3. `apksigner verify --print-certs`：签名有效。
4. **签名证书 SHA-256 必须等于生产 keystore 的证书 SHA-256**：
   - 从 Secrets 仓 `ci/baic2-release.env` 读取 `BAIC2_KEYSTORE_BASE64/PASSWORD/ALIAS`；
   - 解码后用 `keytool -list -v` 取证书 SHA-256；
   - 与 APK signer 比对，不一致直接红灯。
   - 目的：**杜绝发错签名包导致用户必须卸载重装、数据丢失**。
5. `versionCode > 生产 manifest 的 versionCode`；否则跳过并告警，绝不降级。
6. 所有校验失败 → job 红灯，不落盘、不更新 manifest。

### 5.2 新增 Job：`publish-nova-site`

在 `deploy.yml` 增加独立 job，`needs: [deploy]`，部署完成后执行；不构建、不依赖 AutoJs6 子模块、不产生 Actions 制品。

步骤：

1. 按 5.1 取最新稳定 Release（API → 重定向 → Atom）。
2. **版本未变直接跳过（满足“不用上传”）**
   - 从生产域名匿名拉取当前 manifest：
     `https://autojs6.80fafa.com/download/haocanmou/manifest.json`
   - 若 `version` 与 `sha256` 都相同，且 APK HEAD 200 → 输出 `unchanged, skip`，本 job 结束。
   - 若版本相同但 `sha256` 不同（同 tag 重打）→ 继续，覆盖该版本目录。
   - 若线上 `versionCode` 大于本次 Release（回滚/手工热修）→ 跳过并告警，绝不降级。
3. 按 5.1 完成下载与硬校验。
4. **上传并落盘（幂等 + 保留 3 版）**
   - APK 先 scp 到 `/tmp/hk_nova_stage/`。
   - 服务器执行新增的 `RefConf/hk/nova_sync.py`（幂等脚本，见 5.3）。
   - 目录结构：

     ```
     /data/www/web-dist/download/haocanmou/
       manifest.json
       v0.3.7/haocanmou-v0.3.7-arm64-v8a.apk
       v0.3.6/haocanmou-v0.3.6-arm64-v8a.apk
       v0.3.5/haocanmou-v0.3.5-arm64-v8a.apk
     ```

   - `manifest.json` 原子写（`.tmp` → `os.replace`），保留最新 3 个版本目录，其余删除。
   - `deploy.sh` 只清 `download/` 之外的内容，新目录不会被清掉。
5. **发布后冒烟**
   - `GET /download/haocanmou/manifest.json` 返回的版本 == 本次版本。
   - 最新 APK URL `HEAD 200` 且 `Content-Length` 与 manifest 一致。
   - 历史版本数量 ≤ 3。
   - 失败则 job 红灯（不静默 warn）。

> Job 环境补充：`publish-nova-site` 需要 `actions/setup-java@v5`（JDK 17）以使用 `keytool`/`apksigner`；Android build-tools 用 runner 预装的 `$ANDROID_SDK_ROOT/build-tools/*`。签名校验用的 `BAIC2_KEYSTORE_*` 从 Secrets 仓 `ci/baic2-release.env` 读取，SSH 凭据从 `ci/hk-deploy.env` 读取；主仓仍只需要现有的 `SECRETS_REPO_PAT`，**不新增 GitHub Secret**。GitHub Release 读取本身匿名，不需要任何 PAT。

### 5.3 `RefConf/hk/nova_sync.py` 职责

输入：APK 路径、version、versionCode、publishedAt、sha256、size、notes、source（repo/tag/releaseUrl）、目标根目录。

行为：

1. 读现有 `manifest.json`（不存在则空历史）。
2. 若同 version 已存在：替换文件与元数据；否则插入。
3. 按 `versionCode` 降序排序，保留前 3，删除其余版本目录。
4. 把新 APK 移入 `v<version>/haocanmou-v<version>-arm64-v8a.apk`。
5. 重新生成 `manifest.json`（含 `files` 最新项 + `history` 最多 3 项）。
6. 输出变更摘要；重复执行结果一致。

- 管理仓 push `v*` tag 或手动 Run 是**唯一同步契机**；不设每日定时同步。
- NovaBAIC 独立发版，与管理仓 tag 无版本绑定；管理仓 tag 只触发“去拉取最新稳定 Release”，不会改写客户端版本号。

- 产品发布节奏因此是：**先发 NovaBAIC Release，再推管理仓 tag（或手动 Run）让生产可见**。
- 只同步正式稳定版：主路径按 `releases` 列表过滤 `draft/prerelease` 后取最高 semver；`releases/latest` 仅作兜底。若将来需要灰度/预发布，另开显式开关，不在本次范围。

### 7.2 检查时机

- **进程级只检查一次**：`AppUpdateManager` 用 `AtomicBoolean` 去重；MainActivity 与 FloatBallService 都调用也不会重复请求。
- **冷启动空闲检查**：延迟 3 秒（常量可调）后发起，不阻塞启动、不抢占登录/首屏。
- **触发入口**：
  - `MainActivity.onCreate` 的 `UpdateGate`：覆盖“用户从桌面点开”的路径；
  - `FloatBallService.onCreate`：覆盖“开机/保活拉起、没有 MainActivity”的路径；
  - 设置页“检查更新”：用户手动触发，绕过进程级去重。
- **请求**：`GET {SERVER_ORIGIN}/download/haocanmou/manifest.json?t=<now>`，`Cache-Control: no-cache`，本次调用 15s 超时；失败只记录，不打扰。
- **Debug 构建**：默认不参与强制更新；只有 `local.properties` 配了 `dev.updateManifestUrl` 才启用，便于本地模拟。

### 7.3 状态机与 UI

```
Idle → Checking → UpToDate
                → OptionalAvailable（可关）→ Downloading → ReadyToInstall → Installing
                → ForcedAvailable（不可关）→ Downloading → ReadyToInstall → Installing
                → CheckFailed（不打扰，保留缓存强制态）
```

- **可选更新**：
  - 只在已登录、主界面可见时弹出；不打断悬浮球参谋会话。
  - 文案：“服务器端有新版本可用 v0.3.8”，展示大小/更新说明；按钮“立即升级”“稍后”。
  - “稍后”本次关闭，下次启动再次提示（不记忆忽略，符合“每次启动检查”）。
- **强制更新**：
  - 全屏页面（复用 `AdvisorPage` 统一顶栏/主题），标题“必须更新后才能继续使用”。
  - 拦截返回键，不显示登录页、不显示主界面、不启动悬浮球。
  - 自动开始下载；下载完成自动拉起系统安装器。
  - 失败时显示原因与“重试下载/重新安装/去开启安装权限”；允许“退出应用”，但不允许继续使用。
- **下载中**：显示进度百分比/已下载大小；可选更新可取消，强制更新不可取消。
- **安装等待**：拉起系统安装器后提示“请在系统弹窗中确认安装”；App 被系统替换后由 `MY_PACKAGE_REPLACED` 拉起服务。

### 7.4 强制拦截的范围（不能有绕过口）

`AppUpdateManager` 持久化 `forced_version_code`（SharedPreferences，`float_update`）：

- `MainActivity`：强制态优先于登录门、主界面、悬浮窗权限门。
- `FloatBallService.onCreate`：强制态直接 `stopSelf()`，并按现有登录门的同一套收尾逻辑取消保活/检点，避免“拉起→停服”循环；尽力发出“需更新”通知，用户点开进强制页。
- `KeepAliveBootReceiver` / 心跳：最终都会经过 `FloatBallService.onCreate` 的强制门。
- **断网不能绕过**：若本地已缓存强制版本且本机仍低于它，即使 manifest 拉取失败也继续拦截；只有成功拉取到“不高于本机”的 manifest 才清除强制缓存。
- **服务端后续可加**：若需要防改包绕过，可在 API 网关注入 `X-Client-Version` 并在低于最低版本时返回 426；本次不做，避免扩大改动面。

### 7.5 下载与校验

1. 选择 manifest 中 `abi == arm64-v8a` 的文件；核对 `packageName == com.verlintas.baic2`。
2. 检查 `cacheDir` 可用空间 > `size * 1.2`；不足提示清理。
3. 下载到 `cacheDir/updates/<version>.apk.part`：
   - 带 `Range` 断点续传；已存在 `.part` 时从断点继续；
   - 每次进度写入 `StateFlow`，UI 展示；
   - 完成后 `sha256` 必须与 manifest 完全一致，否则删除并报“下载校验失败”；
   - 去掉 `.part` 后改名为 `<version>.apk`；
   - URL 追加 `?v=<sha8>` 破缓存。
4. 不新增下载服务/WorkManager；下载协程属于 App 单例，进程被系统杀掉后下次启动从 `.part` 继续。强制页停留期间下载持续进行。

### 7.6 安装与“覆盖升级不丢数据”

安装前**三重校验**（任何一项失败都不拉起安装器）：

1. `versionCode > 当前安装 versionCode`；
2. `packageName == com.verlintas.baic2`；
3. **APK 签名证书 == 当前已安装 App 的签名证书**（SHA-256 集合比对；API 26–27 用 `GET_SIGNATURES`，28+ 用 `GET_SIGNING_CERTIFICATES`）。

安装方式：

- 未授予“安装未知应用” → 跳 `Settings.ACTION_MANAGE_UNKNOWN_APP_SOURCES`，返回后重试；
- 已授予 → **系统 `PackageInstaller` 会话安装**：`createSession(MODE_FULL_INSTALL)` 经 `openWrite` 写入 APK，
  `commit()` 传 `PendingIntent` 到 `UpdateInstallReceiver`；`STATUS_PENDING_USER_ACTION` 时由接收器拉起系统确认界面。
  不经过 `content://`/FileProvider（2026-10-26 真机 E2E 实测：MIUI/HyperOS 安装器中转第二个 Activity 后会丢失
  URI 授权，报 `Permission Denial: ... FileProvider ... that is not exported`，改 PackageInstaller 后通过）。
- 系统安装器会要求用户点一次“安装/更新”。这是 Android 对普通应用的平台限制；**不做 Shizuku 静默安装**（避免 stdin/私有目录读取的易碎实现），保证稳定与可维护。
- 安装完成后系统会终止旧进程；用户点“打开”或从桌面启动新版本。

**数据保留的机制与保证**：

| 数据 | 升级后是否保留 | 原因 |
| --- | --- | --- |
| 账号会话（`float_account` SharedPreferences） | 保留 | 同包名同签名的覆盖安装保留 App 数据目录 |
| 卡密/钱包快照 | 保留 | 同上 |
| 好参谋设置（`floatball_advisor`） | 保留 | 同上 |
| Room 会话/记忆/画像数据库 | 保留 | 同上，新版本自行做 Room migration |
| Android Keystore 加密密钥（`baic2_secret_v1`） | 保留 | 密钥绑定 App UID，覆盖安装 UID 不变 |
| **装包登录门** | **必须改** | 现状任何安装/升级后首启都强制登录，是本次唯一必须改的代码 |

**装包登录门改造（硬性要求）**：

```kotlin
// AccountManager
/**
 * 仅“全新安装”强制先登录；覆盖升级必须保留登录态。
 * 规则：
 *  - 本机已有登录过的时间戳（非 0）→ 永不因安装/升级触发登录门；
 *  - 时间戳为 0 且当前无会话 → 全新安装，触发登录门；
 *  - 时间戳为 0 但已有有效会话 → 旧版本遗留升级，按升级处理，补记时间戳。
 */
fun installGatePending(): Boolean =
    prefs.loadInstallGateTime() == 0L && !isLoggedIn

fun consumeInstallGate() {
    prefs.saveInstallGateTime(System.currentTimeMillis())
}
```

- `MainActivity` 去掉 `packageUpdateTime` 与 `lastUpdateTime` 比较；
- 登录成功调用 `consumeInstallGate()`；
- 旧版本升级用户（有会话、时间戳 0）首启不弹登录，并立即补记时间戳，后续稳定。

> 边界：用户主动退出登录后升级 → 仍出登录页（因为本来就没有会话），符合预期；全新安装仍先登录，安全口径不变。

## 8. 安全与失败策略

| 风险 | 处理 |
| --- | --- |
| 下载到篡改包 | HTTPS + manifest SHA-256 + APK 签名与当前安装包一致 + versionCode 递增 |
| 发错签名包导致用户必须卸载 | CI 用生产 keystore 指纹校验 APK，签名不一致直接红灯 |
| 老版本被降级 | manifest 只前进不后退；服务器 `versionCode <= 线上` 跳过；App 端也要求 `versionCode > 本机` |
| 断网绕过强制更新 | 本地缓存强制版本；成功拉取到不高于本机的 manifest 才清除 |
| 服务器不可达 | 不阻塞普通使用；有强制缓存时按缓存拦截 |
| 安装权限未开 | 明确跳转设置 + 返回后重试，不静默失败 |
| 安装被用户取消 | 可选更新提示“已取消”；强制更新保持拦截并提供“重新安装” |
| 磁盘不足 | 下载前检查，提示清理；删除旧 `.part`/旧版本 APK |
| 缓存旧 APK | URL 带 `?v=<sha8>`；manifest 响应 no-cache |
| GitHub API 限流 | `releases/latest/download` 重定向兜底；必要时才加只读 PAT |
| NovaBAIC 转私有 | 在 Secrets 仓新增 `NOVA_RELEASE_TOKEN`（仅 Contents: Read-only），代码留好可选读取分支 |
| 发布包多 ABI/改名 | API 的 `assets[]` 动态选择；优先 arm64；不唯一则失败，不猜 |

## 12. 需要您批准/确认的点

1. **强制更新时是否允许“退出应用”按钮**：默认保留（不允许继续使用，但允许退出）。
